## 한 문장 요약

테스트 시점 AI-for-AI 문제에서, Builder가 Target의 가중치를 고정한 채 Target의 실행 피드백으로부터 '언제 지원이 필요한지'와 '어떤 자원을 제공할지'를 규정한 Meta-Skill을 학습해 재사용 가능한 스킬 뱅크로 고정한 뒤 미지의 과제에 대해 실행 환경(harness)을 구성하여 성능을 향상시킨다.

## 해결하려는 문제

기존 연구는 주로 에이전트의 추론 능력 자체를 개선하는 데 초점을 맞추었으나, 에이전트가 행동하는 실행 환경(환경 설계)이 성능에 미치는 영향과 이를 학습적으로 개선하는 문제는 상대적으로 다루어지지 않았다. 본 논문은 Target과 Builder라는 두 역할을 분리하고, 두 모델의 가중치를 고정한 상태에서 Builder가 어떻게 Target의 실행을 돕기 위해 더 나은 실행 환경(허니스)을 구성할 수 있는지, 그리고 그 경험을 재사용 가능한 형태로 일반화할 수 있는지를 묻는다. 또한 단순히 동일한 지원 자원(스킬 뱅크)을 Target에게 곧바로 제공하는 것보다, Builder가 구성한 환경을 통한 지원이 더 효과적인지 검증하고자 한다.

## 핵심 기여

- 테스트 시점 AI-for-AI 문제 설정과 Builder/Target 역할 분리를 제안함(두 모델의 가중치 고정).
- Meta-Skill 개념을 도입하여 '언제 지원이 필요한지'와 '어떤 자원을 제공할지'를 규칙화·실행 가능한 원칙으로 정의함.
- Builder가 Target의 실행 피드백(개발셋)을 이용해 Meta-Skill을 학습하고 이를 고정한 스킬 뱅크로 보관하여 미지의 과제에 재사용하는 학습·운영 절차를 제안함.
- 실험적으로 Harness-Bench와 NewtonBench에서 Meta-Skill 기반 전체 뱅크(full-bank)가 성능을 실질적으로 향상시킨다는 정량적 증거를 제시함(구체적 향상 수치 포함).
- 같은 모델이 Builder와 Target 역할을 모두 수행할 때의 이득을 관찰하여 시스템 수준의 자체 개선(self-improvement) 가능성을 시사함.

## 접근 방법

* 본문(초록)에 따르면 접근은 다음과 같다.
* Builder는 Target의 실행 중 발생하는 피드백을 개발셋에서 관찰하여 Meta-Skill을 학습한다.
* Meta-Skill은 언제(situations) 지원이 필요한지와 어떤 자원(resources)을 제공해야 하는지를 규정하는 원칙이다.
* 학습된 Meta-Skill들은 스킬 뱅크(skill bank)로 고정(frozen)되어 보관되고, 테스트 시점에는 Builder가 이 고정된 스킬 뱅크를 사용해 주어진(미지의) 과제에 대해 적절한 실행 환경(harness)을 구성한다.
* 논문 본문(초록)에는 아키텍처 상세, 학습 알고리즘, 스킬의 표현 형식, 최적화 절차 등 구체적 구현 세부사항은 제시되어 있지 않다.

## 주요 결과

- 실험 데이터셋: Harness-Bench 및 NewtonBench에서 평가함(초록의 언급).
- 정량 결과(초록 기준): full-bank meta-skills는 no-skill construction 대비 매크로 평균(macro-average) 성능을 8.95 percentage points 향상시켰음.
- 정량 결과(초록 기준): 동일한 스킬 뱅크를 Target에 직접 제공(direct delivery)한 경우와 비교하여 full-bank meta-skills는 12.02 percentage points 더 나은 매크로 평균 성능을 보였음.
- 추가 관찰: 동일한 모델이 Builder와 Target 역할을 모두 수행할 때도 성능 이득이 관찰되어 시스템 수준의 자기개선 경로를 시사함(수치 미제공).

## 한계

- 저자 명시(본문에 드러난 제약): 두 모델(Builder·Target)의 가중치는 고정되어야 한다는 설정이 전제되어 있음(학습 가능한 파라미터 업데이트를 통한 개선을 다루지 않음).
- 저자 명시(본문에 드러난 제약): Builder는 Target의 실행 피드백을 개발셋에서 필요로 하므로 개발셋상의 실행 로그/피드백 접근이 전제됨.
- 추정(본문 범위에서 확인되는 제약): 실험이 Harness-Bench와 NewtonBench 두 벤치마크에 한정되어 있어 다른 도메인·대규모 실세계 응용으로의 일반화성은 불명확함.
- 추정(본문 범위에서 확인되는 제약): 메타-스킬의 표현 방식, 학습 알고리즘, 하이퍼파라미터, 계산 비용 및 런타임 오버헤드 등 구현·운영 관련 상세가 본문(초록)에서 확인되지 않아 재현성·배포 비용에 대한 정보가 부족함.

## 개발자 관점

- 재현성: Builder가 Target의 실행 피드백(개발셋 로그)에 접근할 수 있어야 하며, 동일한 피드백 수집·전처리 파이프라인을 재현하는 것이 중요하다.
- 구현/버전관리: 학습된 Meta-Skill은 '고정된 스킬 뱅크'로 버전 관리해야 하며, 테스트 시점에 Builder가 해당 뱅크를 불러와 harness를 구성하도록 운영 파이프라인을 설계해야 한다.
- 운영 비용: Builder가 추가로 실행되어 허니스(harness)를 구성하는 과정은 런타임·컴퓨팅 오버헤드를 야기하므로 실제 배포 환경에서는 지연(latency) 및 비용을 측정·최적화할 필요가 있다.
- 안전성·검증: 허니스가 Target의 행동을 바꿀 수 있으므로 제공되는 자원과 구성 규칙이 의도치 않은 바람직하지 않은 행동을 유발하지 않는지 검증할 검증·필터링 메커니즘이 필요하다.
- 평가 설계: 성능 평가에 매크로 평균을 사용했으므로 클래스 불균형·태스크 분포를 고려한 추가 지표(마이크로 평균, per-task breakdown 등)를 함께 보고하는 것이 실무 적용에 유리하다.
