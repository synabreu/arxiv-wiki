## 한 문장 요약

소프트웨어 개발 수명주기(SDLC)와 이를 모니터링하는 에이전트형 AI 구성요소를, LLM 지원의 전문 보안 에이전트 집합과 에이전트별 암호화 서명 어테스테이션을 퍼미션드 블록체인 스마트컨트랙트에 기록하여 무결성·출처 검증과 배포 결정의 검증 가능성을 제공하는 블록체인 기반 에이전트 보안 프레임워크를 제안한다.

## 해결하려는 문제

논문은 SDLC 전반과 SDLC를 모니터링하는 '에이전트형 AI'의 신뢰성(무결성, 출처 추적, 배포 결정의 검증 가능성)을 확보할 필요를 문제로 삼는다. 구체적으로 본문은 중앙화된 신뢰 기반이나 수작업 감사만으로는 에이전트의 분석·결과·결정이 변조되거나 추적 불가능해질 수 있으며, LLM 기반 에이전트들이 생성하는 분석 결과를 신뢰 가능한 방식으로 기록·검증하고 자동화된 정책 집행(허용/차단)을 연결하는 방법이 필요하다고 전제한다. 연구 질문은 '에이전트형 AI가 생성하는 분석·결정의 무결성과 검증 가능성을 어떻게 보장하고, 이를 SDLC의 배포 의사결정에 안전하게 연결할 것인가' 이다.

## 핵심 기여

- SDLC 전반과 에이전트형 AI 구성요소를 보호하기 위한 블록체인 기반 에이전트 보안 프레임워크 제안.
- 소스 무결성, 의존성·SBOM 분석, CI 구성 감사, 아티팩트 검증, 런타임 정책 평가 등 역할별 전문 보안 에이전트 군을 설계하고, 각 에이전트를 LLM으로 지원하여 아티팩트 해석·도구 출력 추론·구조화된 보안 리포트 생성하도록 한 점.
- 에이전트 신뢰성 확보를 위해 각 에이전트가 암호화 서명된 어테스테이션을 생성하고 이를 권한형(퍼미션드) 블록체인의 스마트컨트랙트를 통해 기록하는 아키텍처(에이전트 레지스트리, 불변 어테스테이션 로그, 집행 가능한 릴리스 정책 모듈)를 제시한 점.
- 에이전트와 블록체인 노드 간 통신을 컨소시엄 운영의 인증기관(CA)으로 보호하여 인증·변조저항성을 확보하는 통신 보안 설계 제안.
- 소스 코드 보안 에이전트의 분석→온체인 어테스테이션 고정→검증가능한 허용/차단 배포결정 트리거에 대한 상세한 유즈케이스 및 시퀀스 흐름을 제시하여 아키텍처 동작을 구체적으로 설명한 점.

## 접근 방법

* 본문에 제시된 방법은 모듈화된 아키텍처와 온체인 어테스테이션 워크플로로 요약된다.
* 핵심 구성요소는(1) 역할별 전문 보안 에이전트 군(소스 무결성, 의존성·SBOM, CI 구성 감사, 아티팩트 검증, 런타임 정책 평가), (2) 각 에이전트를 보조하는 LLM(아티팩트 해석·도구 출력에 대한 추론 및 구조화된 보고서 생성), (3) 권한형 블록체인과 스마트컨트랙트(에이전트 레지스트리, 불변 어테스테이션 로그, 릴리스 정책 집행 모듈) 및 (4) 컨소시엄 CA 기반의 인증된 통신 채널이다.
* 작동 절차(본문의 서술 기반): 에이전트가 아티팩트나 도구 출력을 LLM으로 분석하여 보안 리포트를 만들고, 그 결과에 대해 암호화 서명된 어테스테이션을 생성하여 스마트컨트랙트에 기록(해시 또는 메타데이터 형태로 온체인 고정)한다.
* 스마트컨트랙트의 릴리스 정책 모듈은 등록된 어테스테이션을 검토하여 배포 허용/차단 결정을 내리고(유즈케이스: 소스 코드 보안 에이전트가 배포 의사결정 트리거) 통신은 컨소시엄 CA로 인증되어 변조저항성을 확보한다.
* 본문에는 사용된 특정 블록체인 플랫폼, 스마트컨트랙트 코드, 합의 알고리즘, LLM 종류·학습·튜닝·추론 파라미터 등 구현·학습·추론의 세부 절차는 제공되지 않는다.

## 주요 결과

- 본문은 제안 프레임워크의 개념 설계와 '소스 코드 보안 에이전트' 유즈케이스 및 시퀀스 흐름(분석→온체인 어테스테이션→검증가능한 허용/차단 트리거)을 상세히 제시하나, 실험적 평가나 정량적 결과(데이터셋, 성능 지표, 비교 평가, 처리량·지연·오버헤드 수치)는 제공하지 않는다.
- 비교 대상이나 벤치마크 실험이 본문에 언급되어 있지 않아 성능·확장성·에너지 소비·보안 이득을 수치로 증명한 결과는 없다.

## 한계

- 저자가 본문에서 명시한 한계: 본문(제공된 본문/요약)에는 저자가 직접 기술한 한계나 실험적 제약에 대한 명시적 서술이 포함되어 있지 않다.
- 합리적으로 확인되는 한계(본문 근거 기반):
- 구현 세부사항 부재 — 특정 블록체인 플랫폼(예: Hyperledger, Fabric, Besu 등), 스마트컨트랙트 구현, 합의 메커니즘, 온체인에 저장되는 데이터의 정확한 스키마(원문/해시/메타데이터) 등이 제시되지 않아 재현 불가.
- LLM 관련 미기술 — 어떤 LLM을 사용하며(사전학습/미세조정 여부), 프롬프트·체인오브툇크(Chain-of-Thought) 사용, 추론 지연/비용/신뢰성(환각)에 대한 대비책이 제시되지 않음으로써 에이전트 출력의 신뢰성 확보 방법이 불명확함(오류·환각 대응 전략 부재).

## 개발자 관점

- 재현·구현: 논문은 개념·아키텍처 중심이므로 실제 구현 시 선택해야 할 요소가 많다. 권한형 블록체인 플랫폼(예: Hyperledger Fabric)과 스마트컨트랙트 언어를 먼저 결정하고, 온체인에 저장하는 것은 전체 리포트가 아닌 서명된 리포트의 해시·메타데이터로 최소화해 온체인 비용과 개인정보·비밀 누출 위험을 줄여야 한다.
- LLM 통합: LLM은 문맥 해석·분석 보고서 생성에 사용되므로 모델 선택(대규모 공개모델 vs 사내 파라미터화된 모델), 프롬프트 엔지니어링, 출력 검증(규칙 기반 체크, 2차 검증 에이전트 또는 도구 체인) 설계가 필요하다. 환각 방지를 위해 LLM 출력에 대한 도구(정적 분석기, SBOM 검사기 등) 교차검증을 도입하라.
- 보안·키관리: 에이전트 서명용 키는 HSM 또는 KMS에 안전히 보관하고 키 유출 방지를 위한 롤오버·감사 정책을 마련하라. 컨소시엄 CA는 운영·거버넌스 모델을 명확히 정의해야 하며, CA 자체의 신뢰성·탈중앙화 요구사항을 검토해야 한다.
- 온체인 설계·성능: 블록체인에 반복적으로 어테스테이션을 기록하면 처리량·지연·비용(및 에너지 소비)이 문제될 수 있으므로 어테스테이션 빈도·데이터 크기 조절, 배치 처리, 오프체인 저장+온체인 해시 접근 방식 등을 고려하라.
- 배포·운영: 자동화된 허용/차단 정책을 온체인으로 집행할 때는 '인간 확인' 단계(예: 임계값 초과 시 수동 검토)를 포함해 잘못된 차단의 위험을 줄여라. 또한 정책의 버전관리와 롤백 메커니즘을 설계하라.

**근거 범위:** 논문 PDF 본문 기반 분석: 제공된 본문이 논문 초록 또는 요약 형태로만 추출되어 본문 전반의 상세 구현·실험·정량 결과가 포함되지 않았음. 따라서 아키텍처·유즈케이스·주장된 설계는 본문에서 확인된 내용으로 정리했으며, 구체적 구현 세부사항(플랫폼, 모델 종류, 스마트컨트랙트 코드)과 정량적 평가(데이터셋·메트릭·성능 수치)는 본문에 명시되어 있지 않아 분석에 포함하지 않았다.
