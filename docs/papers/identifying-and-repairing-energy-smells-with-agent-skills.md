## 한 문장 요약

DR. GREENS라는 에이전트 스킬을 제시해 12개 카테고리·65개 근본원인으로 정리된 에너지 냄새에 기반해 파이썬 함수 단위로 냄새를 탐지하고, 입력 생성기와 독립 검증기를 통해 동작을 보존하면서 측정 기반으로 수리를 수행해 에너지 절감을 검증한다.

## 해결하려는 문제

기존 도구들은 정적 규칙에만 의존해 런타임 맥락과 실제 에너지 절감을 검증하지 못하고, LLM 기반 최적화는 주로 실행 시간(속도)을 목표로 하며 에너지 냄새 정의로 변경을 근거화하지 못한다. 또한 에너지 절감 여부는 하드웨어·워크로드·입력에 따라 달라지므로 측정 기반의 반복적 검증 과정이 필요하며, 에이전트가 스스로 측정 흐름을 조작하는 것을 방지할 독립적 입력 생성기·검증기가 요구된다.

## 핵심 기여

- DR. GREENS: Claude 에이전트용 에이전트 스킬로 에너지 냄새 탐지·수리·검증의 전체 워크플로우를 패키징함.
- 에너지 냄새 지식 기반: 12개 에너지 냄새 범주와 65개 근본원인 카드(정의·예제·near-miss 포함) 및 230개의 실측 전·후(수리 케이스)를 제공함.
- 정적 분석기: Python AST 기반 40개 신규 규칙과 Ruff 규칙 31개를 결합해 총 49개 근본원인을 커버하는 규칙 집합을 제공함.
- 검증 기반 측정 파이프라인: CodeGreen 에너지 프로파일러, DEEPSEEK V4.1 Flash 기반 입력 생성기, 독립 검증기를 통해 동작 보존과 에너지 차이를 페어드(protocol) 측정으로 판단함.
- 평가: 세 개 오픈소스 저장소(함수 수: 443, 2,543, 95), 두 모델(Claude Sonnet 5.5, Haiku 5.5), 세 가지 스킬 구성( CORE / CORE+TAX / FULL )로 18개 세션을 실행하고 결과·데이터를 공개(복제 패키지).

## 접근 방법

* 아키텍처: DR.
* GREENS는 에이전트 스킬로 동작하며 세 수준의 지식(분류 인덱스, 카테고리 카드, 근본원인 카드)을 점진적 공개(progressive disclosure) 방식으로 제공한다.
* 추가로 정적 분석기(40 규칙 + 31 Ruff 규칙), 에너지 프로브(CodeGreen), 입력 생성기(DEEPSEEK V4.1 Flash), 독립 검증기를 포함한다.단계별 절차: Step 1 Find — 에이전트가 리포지토리 내의 모든 함수를 읽어 '의심'을 기록(각 의심에 대해 관련 근본원인·라인·이유 포함).
* 정적 분석기가 활성화된 경우 분석기 결과와 대조해 놓친 항목을 보완한다.Step 2 Decide — 근본원인 카드와 near-miss를 열람해 각각의 의심을 심층 검토하고 동작 보존 여부(에지 케이스 포함)를 판단해 수리 대상 수락/거부.Step 3 Repair and Measure — 에이전트가 수리안을 작성해 제출하면 입력 생성기는 에지 입력 몇 개와 네 개의 '측정용' 고부하 입력을 생성한다.
* 측정용 입력은 원본 코드에서 에너지를 많이 쓰는 상위 후보 4개를 선택(LLM이 8개 후보를 쓰고 그중 4개를 채택).
* 검증기는 각 입력에서 원본과 수리본의 반환값·인수 상태·출력·파일 변경 등을 비교해 동작 동등성 검증을 수행하고, 동작이 동일하면 CodeGreen과 페어드 프로토콜(각 입력에 대해 9쌍 실행, 쌍별 차이에 대해 Student's t로 95% 신뢰구간)으로 에너지 차이를 측정해 판정(confirmed/partial/mixed/regressed/negligible/inconclusive).
* 세션 후 모든 시도 수리를 재측정(재검증)해 에이전트 내부 측정의 영향을 배제.구현 세부: 함수 단위 분석, 함수당 하나의 권장 수리만 적용(동등성을 유지하는 것 중 평균 절감이 가장 큰 수리 선택), 정적 분석 규칙은 근본원인에 매핑되어 보고를 보조하되 문맥 판단은 에이전트가 수행.

## 주요 결과

- 수리 제출 및 판정: 에이전트들이 제출한 수리 317건 중 258건이 측정(verdict)까지 도달함.
- 주요 정량 결과: 측정된 258건 중 68.6%가 에너지 절감(95% CI 63.3%–73.2%, 부트스트랩 over 18 세션, 10,000 재표본)이며, 절감의 중앙값은 24.9% (95% CI 17.8%–26.7%).
- 모델별: Sonnet의 측정 수리 중 67.3%가 절감, Haiku는 70.7%로 두 모델에서 유사한 비율을 보임.

## 한계

- 저자가 명시한 한계: (1) 구성 타당도: 세션에서 사용하는 네 개의 측정 입력이 실제 운영 데이터 분포를 대표하지 않을 수 있음(저자는 입력 생성 조건과 코드 커버리지 기준으로 완화 시도). (2) 내부 타당도: 에너지 측정에 잡음이 존재할 수 있음 — 이를 전용 머신에서 순차 실행, 페어드 측정, 노이즈 플로어 측정 등으로 완화. (3) 외적 타당도: 세 저장소와 Python 중심의 샘플링은 범용성에 한계가 있으며 더 많은 저장소·언어에서 결과를 확인해야 함.
- 본문에서 합리적으로 확인되는 한계(저자 언급과 구분): (1) 측정 오버헤드·시간 비용: 각 수리는 여러 입력에 대해 반복 실행(9쌍 등)과 재측정을 요구하므로 대규모 리포지토리 전체 자동화 시 시간·자원 부담이 클 것으로 추정됨. (2) 도구 의존성: 평가와 판정은 CodeGreen, DEEPSEEK, Claude 모델 등 특정 도구·모델·하드웨어에 의존하므로 다른 측정 인프라·모델에서 동일한 결과가 보장되지 않음. (3) 함수 단위 한계: 수리 단위를 함수로 고정했으므로 교차 함수·모듈 전반의 구조적 변환에는 직접 적용하기 어렵다. (4) 비결정적·외부 영향: 비결정적 행동(외부 I/O, 난수 등)을 가진 함수는 입력 생성·검증에서 배제되거나 증명 실패로 이어질 수 있음.

## 개발자 관점

- 재현·배포: 논문은 코드·스킬·데이터를 공개한 복제 패키지(저자 제공 GitHub)를 제공하므로 복제하려면 전용 측정 머신(노이즈 최소화), CodeGreen 같은 정밀 에너지 프로파일러, DEEPSEEK 등 입력 생성 도구, Claude 에이전트 권한(명령 실행) 환경이 필요하다.
- 구현·통합: 에이전트 스킬은 세분화된 지식 카드(인덱스→카테고리→근본원인)를 점진적으로 제공하는 구조가 핵심이다. 정적 분석기 규칙을 근본원인에 매핑하면 에이전트의 검색 회수(리콜)를 높일 수 있다.
- 운영 비용: 각 수리 검증에 다수의 실행(페어드 프로토콜, 9쌍/입력, 4 입력 + 재측정)이 필요하므로 CPU 시간·전력·검증 시간 비용이 발생한다. 실무 도입 시 전체 릴리스 전 또는 CI 파이프라인의 선택적(예: 변경된 함수만) 실행으로 비용을 통제해야 한다.
- 안전성·신뢰성: 독립 검증기(에이전트 외부)로 동작 보존을 확인하고 입력 생성기를 에이전트와 분리해 에이전트가 측정 입력을 편향시키는 것을 방지하는 설계가 중요하다. 또한 '동등성 기준'은 반환값·인수 상태·출력·파일 변경을 포함하도록 엄격히 구성해야 한다.
- 실무 적용 팁: (1) 우선 정적 분석기를 커밋 훅 또는 CI에서 실행해 후보 탐지(저비용), (2) FULL 스킬은 릴리스 직전 또는 고비용 함수에 대해 측정 기반 검증 수행, (3) 함수 단위로 한 개 수리만 추천하도록 하여 충돌 최소화, (4) 비결정적 함수는 우선 제외하거나 별도 테스트 전략을 준비할 것.
