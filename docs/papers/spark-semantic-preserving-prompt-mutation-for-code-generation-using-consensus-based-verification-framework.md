## 한 문장 요약

SPARK는 원문과 의미 보존(prompt-preserving)된 변형 프롬프트들을 생성하고 각 변형에서 코드와 테스트를 생성한 뒤 합의 기반 검증(consensus-based validation)으로 가장 일관된 동작을 보이는 코드를 선택해 코드 생성의 신뢰도와 pass@1 성능을 향상시키는 방법이다.

## 해결하려는 문제

기존의 LLM 기반 코드 생성에서는 실제 환경에서 사람이 작성한 완전한 테스트 수트가 부족해 생성된 코드의 자동 검증이 어렵고, 단일 프롬프트에 의존할 경우 LLM이 사소한 명세 해석 차이로 잘못된 코드를 반복 생성해 합의 기반 검증(CodeT 등)도 잘못된 후보를 선택할 수 있다. 본 논문은 이러한 한계를 해결하기 위해 의미를 보존하는 프롬프트 변형을 통해 코드·테스트 생성의 다양성을 늘리고, 변형 간 일관된 동작을 보이는 구현을 합의 기반으로 선택하는 것을 목표로 한다.

## 핵심 기여

- 의미 보존(semantic-preserving) 프롬프트 변형 연산군(문맥, 스타일, 동사, 어조 변형 등 14종)을 정의하고 GPT-4o로 자동 생성하여 코드 및 테스트 생성의 다양성을 유도하는 SPARK 프레임워크를 제안.
- 각 변형으로부터 생성한 코드 후보와 테스트를 사용해 dual-execution(합의 기반) 검증을 수행하고, 테스트 통과 패턴에 기반한 군집 점수 f(S)=|Sx|·|Sy|로 최종 솔루션을 선택하는 알고리즘을 제시.
- 세 가지 상호보완적 벤치마크(LiveCodeBench, BigCodeBench, DLBench)와 세 모델(o4-mini, DeepSeek R1 Basic, Gemini 2.5 Pro)을 대상으로 광범위한 평가를 수행하고, 튜닝된 변형 조합으로 기존 합의 기반 기법(CodeT 등)을 평균 최대 +4.1% (pass@1)까지 능가함을 보임.
- 프롬프트 변형이 코드/테스트 다양성, 룩업 방지(lookup prevention), 엣지케이스 검사, 명세(간접 요구사항) 명확화 등으로 성능 향상에 기여하는 메커니즘을 정성 분석으로 규명.
- 코드 품질 지표(Maintainability Index, LCOM1, CBO, Cyclomatic Complexity)를 동작 기반 합의 점수의 동점 해소용 타이브레이커로 결합해 기능적 동등성으로는 구별되지 않는 후보 사이에서 구조적 품질을 고려하는 후처리 전략을 제안.

## 접근 방법

* SPARK는 세 단계로 동작한다.
* (1) Prompt Mutation: 원문 문제 설명에 대해 GPT-4o를 이용해 의미를 보존하는 14개 변형 연산(문맥 변경: 함수명 제거/비관련명/오도명/변수명 변경 등, 스타일 변경: 대소문자/하이라이트, 동사·시제 변경, 어조 변경 등)을 적용해 변형 프롬프트 집합을 만든다.
* (2) Code & Test Generation: 원문과 각 변형 프롬프트로부터 대상 코드 후보와 테스트 케이스를 생성한다.
* 테스트는 세 형식(simple input-output assertion, unittest, pytest)에 맞춰 생성한다.
* 생성된 코드는 누락된 import 삽입, 함수명/변수명 정렬 같은 자동 후처리를 거쳐 실행 가능 상태로 만든다.
* (3) Solution Selection: 모든 코드 후보를 모든 생성 테스트에 대해 실행하여 통과/실패 패턴을 수집하고, Sx(동일한 테스트 부분집합을 통과하는 코드 집합)와 Sy(그들이 함께 통과하는 테스트 집합)의 크기를 곱한 점수 f(S)=\|Sx\|·\|Sy\|로 군집을 평가해 최고 점수 군집의 코드를 선택한다.
* 동점 시에는 MI, LCOM1, CBO, CC 등 정적 품질 지표를 정규화·결합한 구조적 품질 점수로 타이브레이킹 한다.
* 실험시 모든 모델은 제로샷, temperature=0.3, top-p=1.0으로 쿼리되었고, 프롬프트 변형 생성은 GPT-4o를 사용하였다.

## 주요 결과

- 평가 환경: LiveCodeBench, BigCodeBench, DLBench 세 벤치마크와 o4-mini, DeepSeek R1 Basic, Gemini 2.5 Pro 세 LLM을 사용.
- 변형 품질: 12,586개 변형 중 무작위 500건 수동 라벨링 결과, 변형이 의도대로 적용된 비율(Applied Correctly)은 전체 평균 95.4 ± 1.8%, 의미 동등성(Semantically Equivalent) 평균 96.4 ± 1.6%, 둘 다 만족 비율은 92.0 ± 2.3%였다. 다만 Declarative→Interrogative의 의미 보존률은 79.6%로 낮았고, Adversarial Function Name 적용 정확도는 88.4 ± 8.5%로 비교적 낮았다.
- 단일 변형 적용 시 성능: Table III 결과에 따르면 단일 변형만 적용해도 모델·데이터셋에 따라 평균 개선이 관찰되었다. 평균 향상(Original→SPARK single mutation)은 o4-mini +3.4%p, DeepSeek R1 +5.1%p, Gemini 2.5 +2.2%p (pass@1 기준, Table III의 평균 행 근거).
- 모든 변형 동시 적용: 모든 변형을 동시에 적용한 SPARK는 항상 최선은 아니며 일부 경우 성능 저하를 보였음(예: BigCodeBench에서 Gemini에 대해 -1.8%p 등).
- 튜닝된 변형 조합: 검증셋으로 변형 조합을 튜닝한 SPARK는 모든 모델·벤치마크에서 강력한 베이스라인을 일관되게 따라잡거나 능가했으며, 최대 평균 +4.1%p(pass@1) 향상을 보고하였다. 통계적 검정(Wilcoxon Signed Rank)에서 p=0.03으로 유의미함을 보고함(본문).

## 한계

- [저자 언급] 동일 LLM로 코드와 테스트를 모두 생성하면 순환성(circularity) 위험이 있어 잘못된 혹은 단순한 테스트를 모델이 만들어 잘못된 구현을 선택할 수 있음.
- [저자 언급] 제안한 LLM 기반 프롬프트 변형군이 실제 현업에서 발생하는 모든 의미·양식 변이를 포괄하지 못할 수 있음.
- [저자 언급] 평가에 사용한 세 벤치마크(LiveCodeBench, BigCodeBench, DLBench)와 Python 테스트 형식은 소프트웨어 엔지니어링의 모든 상황·언어를 대표하지 못할 수 있음.
- [본문 확인] 일부 변형(예: Declarative→Interrogative)의 의미 보존 실패율이 비교적 높아(≈20%) 무분별한 적용 시 성능 저하를 초래할 수 있음; 따라서 변형 선택·검증 과정이 필요함(논문 실험에서 튜닝 필요성을 강조).

## 개발자 관점

- 재현: 코드·데이터 공개(저자 제공 링크)로 재현 가능하지만 실험 재현을 위해서는 GPT-4o(프롬프트 변형용)와 코드 생성용 고성능 LLM(o4-mini, DeepSeek, Gemini 등) 접근이 필요하다.
- 구현·전처리: 생성된 코드의 import 누락, 함수명/변수명 불일치 등 현실적 문제를 자동으로 보정하는 후처리(임포트 삽입, 시그니처 정렬 등)를 구현해야 실험 파이프라인이 동작함.
- 튜닝 권장: 모든 변형을 무분별하게 적용하면 성능이 떨어질 수 있어 검증 셋에서 변형 조합을 선별하는 튜닝 단계가 실전 배포에서 중요하다 (논문에서 튜닝된 SPARK가 최종 성능을 끌어올림).
- 테스트 형식 대응: 각 개발 환경에 맞춰 Simple/assert, unittest, pytest 템플릿을 준비해야 하며, 테스트 실행 시 프로세스 격리·타임아웃·리소스 제한을 반드시 적용해야 안전함.
- 비용·성능 균형: 프롬프트 변형은 토큰 사용량을 크게 증가시킨다(논문에서는 최대 약 4배 수준이라 보고). 실제 배포 시 비용-이득을 고려해 변형 수를 제한하거나 선택적 튜닝을 권장한다 (토큰 비용·지연 고려).

**근거 범위:** 논문 PDF 본문(페이지 1–10)에 근거한 분석이다. 표·실험 수치(예: Table II, III, IV, VI), 수동 라벨링 결과, 합의 스코어 정의, 테스트 템플릿 및 정성 분석 내용은 본문에서 직접 추출했다. 다만 실제 시스템의 하이퍼파라미터 상세(예: 튜닝 절차의 완전한 검색 공간, 변형 조합 최적화 알고리즘의 구현 세부)는 본문에서 높은 수준으로만 기술되어 있어 구체적 재현을 위해서는 저자 코드·데이터와 실험 스크립트를 참조해야 한다.
