## 한 문장 요약

EU AI Act의 기술요구와 공개 벤치마크를 연결해 모델 평가를 자동으로 실행·기록하고, 역할별 가시성·증거 추적·실행단 에너지 계측을 제공하는 오픈소스 자가호스팅 대시보드 VERA를 제안하고, 도구 동작과 사용자 읽기 성능을 실험적으로 평가했다.

## 해결하려는 문제

공개 벤치마크와 기술적 분류(COMPL-AI)는 LLM의 위험 모드를 계측하지만, 실제 기관의 배포심사 흐름에서는 세 가지 문제가 남아 있다: (1) 접근성(access) — 벤치마크가 커맨드라인 중심이라 비엔지니어 심사자가 직접 결과를 탐색하기 어렵다; (2) 불투명성(opacity) — 요구사항 수준 집계가 테스트-항목별 증거와 연결되지 않아 원인 추적이 어렵다; (3) 추적성(traceability) — 보고서가 평가 실행 이후에 작성되면 평가 실행과 문서의 연계가 훼손될 수 있다. 추가로, COMPL-AI가 연결하지 못한 요구사항(예: 환경영향)은 평가 실행 자체에서 측정 가능한 증거가 누락되어 있다. 본 연구는 이 격차들을 해결하고 기관 심사 워크플로에 맞춘 가시화·증거관리 도구를 제시한다.

## 핵심 기여

- 자가호스팅 오픈소스 대시보드 VERA를 제안하여 완료된 평가를 요구사항 수준 결과로 변환하고, 각 점수에서 생산한 벤치마크와 모델 응답으로 확대해 읽을 수 있으며 실행(run) 식별자를 포함한 증거 내보내기를 제공함.
- 환경영향 요구사항에 대해 평가 실행 중 소모한 에너지를 호스트 수준에서 계측해(실행-레벨) 문서화함으로써 기존의 서면 진술을 부분적으로 계측된 증거로 대체함(도구는 CodeCarbon 사용).
- 대시보드 자체로 관리되는 within-subject 사용자연구를 설계·실행해, 동일한 완료된 평가에서 원시 결과파일만으로 읽을 때보다 요구사항 지향 프레젠테이션을 통해 참가자가 더 많은 정답을 추출한다는 증거를 제공함.
- 요구사항 집계가 가독성을 높이는 대신 어떤 벤치마크들이 커버하는지를 숨길 수 있음을 식별하고, 실행을 도달 가능하게 만드는 것만으로는 충분치 않다는 운영상 교훈을 제시함.
- 대시보드, 연구 도구, 분석 스크립트와 배포 프로필을 공개 리포지토리에 릴리스해 재현성과 조직별 적용을 촉진함.

## 접근 방법

* 구현 아키텍처: Python 3.11 백엔드와 TypeScript 단일 페이지 애플리케이션으로 구성되며, Celery+Redis 작업 큐를 사용한다.
* 진입점은 세 가지(커맨드라인, REST, 로그인 불필요한 가이드형 위저드)이고 모든 요청은 단일 선언적 잡(job)으로 표준화된다.
* 워커는 요구사항-대-벤치마크 매핑을 레지스트리로 해석하고(versioned registry/catalog), 로컬 라우터(자가호스팅된 모델 엔드포인트, 예: Ollama)를 통해 벤치마크 러너를 실행한다.
* 항목(item) 점수들은 캐시되고 부트스트랩 신뢰구간으로 집계되어 요구사항별 점수가 생성된다.
* 산출물(bundle)로는 run 파일, 모델카드, per-item 출력, 컨텐츠 다이제스트가 포함된다.
* 기능적 설계요소: (F1) 코드 없이 4단계 위저드로 평가 실행(F1 대응 R1), (F2) 역할별 필터드 뷰(법무/책임AI/데이터과학)(R4), (F3) 설명 가능 집계(요구사항 행을 확장하면 해당 벤치마크와 모델 응답을 노출)(R2), (F4) 벤치마크가 없는 요구사항은 사람 경로로 라우팅(예: 설명가능성, 수정가능성은 루브릭; 환경영향은 실행-에너지 계측)(R2), (F5) 각 실행에 연계된 산출물 자동생성으로 추적성 보장(R3), (F6) 규격·가중치·집계 정책을 설정파일로 분리해 교체 가능하도록 설계(R5).
* 에너지 계측: CodeCarbon 라이브러리를 워커에 훅킹해 실행기간 소모 에너지(kWh)와 계산된 배출량(kgCO2e)을 기록(호스트의 카운터·권한에 의존).
* 실험적 절차: 도구의 작동을 확인하기 위해 네 가지 자가호스팅 오픈-웨이트 모델(Llama 3.1 8B, Qwen2.5 7B, Gemma 2 9B, Mistral 7B)을 Ollama로 서빙하여 5개(논문에서 데모용으로 선택된) 측정가능 요구사항을 15개 벤치마크로 평가(seed=42, 샘플링 예산=150, 프라이버시는 230문서 스캔).
* 사용자 연구: within-subject 디자인으로 모든 참가자가 '원시 파일로 읽기(기본조건)'를 먼저, 'VERA 대시보드로 읽기'를 두 번째로 수행; 각 조건에서 6개의 객관적 사실 질문(총 12문항)을 답하고 클라이언트 시계와 서버 타임스탬프로 시간을 측정하며 서버에서 정답 검증을 수행(세션 고정된 실행 스냅샷에서 정답 키를 생성).

## 주요 결과

- 요구사항 점수와 실행 에너지(표 IV): 네 모델에서의 다섯 요구사항 결과는 다음과 같다(표의 원문 수치 그대로). Robustness R01 = 1.000(모든 모델), Cyber resilience R02 = {Llama 3.1 8B:0.375, Qwen2.5 7B:0.250, Gemma 2 9B:0.375, Mistral 7B:0.500}, Privacy R05 = 0.728(모든 모델, 모델-독립적 스캔), Capabilities R06 = {0.800,0.800,0.800,0.700}, Toxicity R12 = {0.750,0.625,0.750,0.596}. Trust Factor(가중평균, 보안 4요구사항 중심) = {Llama:66.4, Qwen:58.9, Gemma:66.4, Mistral:67.0} (밴드 모두 'orange'). 실행 에너지(kWh) = {0.0169,0.0134,0.0156,0.0139}; 배출(kgCO2e) = {0.00095,0.00075,0.00087,0.00078}; wall time(분) = {85,66,79,68}. 논문은 부트스트랩 구간이 대부분 예산에서는 퇴화(degenerate)했다고 보고함(비감소적 간격은 본문 표에 표기 됨).
- 사용자 연구(완료자 n=10): 동일한 평가에 대해 원시 파일로 읽었을 때 정답 27/60(45%) → 대시보드로 읽었을 때 42/60(70%)로 증가. 페어드 윌콕슨 검정(정확도 기준) 결과 p = 0.016(양측, exact)로 귀무가설 기각(논문은 이 값이 설계 해상도의 한계에 있음 언급). 시간 측정: 참가자별 중앙값 기준에서 질문당 중앙시간은 원시파일 56초 → 대시보드 30초로 감소했으나 페어드 검정에서 p = 0.064으로 유의수준 미달(귀무가설 채택). 쌍별 개선은 일부 질문유형(특히 '밴드·판정 수 집계'와 '약점 순위 매기기')에서 집중적으로 발생했고, '실행된 벤치마크 수 세기'는 원시 로그에서 더 잘 수행됨.
- 사용자 인식: 설문(완료자 9명)에서 도구의 유용성(perceived usefulness) 평균 4.36/5(Cronbach's α = 0.88). 사용 용이성 항목은 일관성이 낮아(α = 0.62) 개별 항목으로 보고되며, '정보 찾기'와 '학습 노력' 항목이 비교적 낮아(각각 평균 3.89, 3.78) 대시보드에서 정보 위치 실패가 관찰됨.
- 위저드로의 단독 실행(비교대상 아님): 위저드로 평가 실행 시도(9명 도달)에서 5명은 1회 시도 성공(중앙값 55초, 범위 22–180초), 4명은 실패(즉시 포기·5분 캡 등). 저자 판단으로 비전문가의 '무인가(unaided) 실행'은 충분히 증명되지 않음.

## 한계

- 저자가 명시한 한계: 연구 디자인 관련 — 조건 순서가 고정되어(항상 '원시 파일' 먼저) 잔류 학습 효과가 대시보드에 유리하게 작용할 수 있으며, 참가자 이탈로 질문 세트 할당이 불균형(8/10이 동일 세트)해 집단간 난이도 균형을 유지하지 못함(본문 Section VI). 참가자 구성 — 대부분 연구자(9/10)로 위험관리·컴플라이언스 실제 심사자 표본이 아님. 표본 크기 작음(n=10 완주)으로 통계적 검정 해상도 제한.
- 저자가 명시한 도구·측정 한계: 에너지 계측은 '평가 실행(run)-레벨'만을 측정하며 모델 훈련 전체 라이프사이클 에너지나 공급자 보고의 '알려진 또는 추정된 모델 에너지'를 대체하지 못함. 또한 벤치마크 합산은 고정 샘플 예산에서의 내부 pass/fail 기준에 따른 값이므로 모델 공개 문서의 정확도 수치와 직접 비교 가능한 재현값이 아님(요구사항 점수는 도구 내 상대비교용).
- 실험적 제약(본문에서 드러난 제약): 논문 실험은 계산 자원 제약으로 전체 12개 측정가능 요구사항 대신 5개만 샘플링(샘플링 예산 150)해 엔드투엔드 경로를 시연함. 사용자 실험의 순서·세트 불균형·소수 표본으로 인해 '인터페이스 효과의 일반화'는 제한적이며 결과는 '읽기 성능 차이'로만 해석해야 함.
- 접근성 문제: 색상만으로 밴드를 구분하는 인코딩(색상 의존)은 색각이상 사용자에 불리하며 저자가 개선을 권고함.

## 개발자 관점

- 규격(요구사항-벤치마크 매핑)과 집계 가중치를 코드에 하드코딩하지 말고 버전 관리 가능한 데이터 파일(registry·catalog)로 분리하라. 이렇게 하면 정책·가중치 논쟁이 코드 릴리스 비용 없이 파일 변경으로 해결되고 각 실행에 피닝(pinning)이 가능해진다.
- 실행별(run-tied) 산출물(모델카드, 데이터시트, export)을 자동으로 생성해 문서 작성 시점과 평가 실행의 추적성을 확보하라. 보고서는 실행ID·컨텐츠 다이제스트와 함께 내보내져야 한다.
- 평가 엔진이 대체(fallback) 메커니즘을 사용한 경우 이를 UI와 산출물에 명확히 표시해 사용자가 '측정 불가 → 대체 검사'를 혼동하지 않게 하라. 미표시는 오판을 초래함(논문 L3).
- 가이드형 위저드는 인증(authentication) 단계 전에 접근 가능하게 두어 초기 진입 장벽을 낮춰라(논문 L1에서 인증이 사용자 이탈을 유발했다고 보고). 단, 엔터프라이즈 프로필에서는 접근 제어를 실행 데이터·민감데이터 접촉 시점에만 적용하라.
- 요구사항 수준의 집계 뷰와 원시 벤치마크 인벤토리(플랫 로그)를 한 클릭 거리로 유지하라. 집계는 가독성을 높이지만 커버리지 추적(어떤 벤치가 실행되었는지)은 별도 뷰에서 더 잘 수행된다(논문 L5, 연구의 pair 4 역전 현상). UI 설계는 두 관점을 모두 빠르게 전환할 수 있도록 해야 한다.  

추가 구현·배포 실무: CodeCarbon를 사용한 실행-레벨 에너지 계측은 호스트의 카운터와 권한에 의존하므로 운영환경에서 권한·정확도 검증을 수행해야 한다. 자체 호스팅 라우터(예: Ollama)로 추적 가능한 로컬 추론만 허용하면 규제 기관 요구(데이터·프롬프트가 제3자 전송 불가)를 충족할 수 있다. 테스트·회귀: 저자는 커밋 기준으로 178개의 백엔드 단위 테스트와 52개의 브라우저 시나리오를 갖추었음을 보고하므로 충분한 자동화된 테스트를 권장한다. 성능·비용: 논문에서 8B 모델 평가(샘플링 예산 150, 15개의 벤치마크 조합)는 Apple M4 Max(36GB)에서 85분이 소요되었으므로(논문 Deployment 섹션) 대규모 전수 평가에는 유의한 컴퓨팅 시간과 자원이 필요함.

**근거 범위:** 이 분석은 제출된 논문 PDF 본문(페이지 1–11)에 근거하여 작성되었다. 본문에 명시된 수치·설계·실험 결과만을 인용했으며, PDF에 명시적으로 나오지 않는 구현 세부사항이나 추가 수치는 추정하지 않았다. 참가자 표본 불균형·작은 표본크기·고정 순서 등 연구자가 본문에서 보고한 제약은 본 요약에 반영하였다.
