## 한 문장 요약

SHACL의 cardinality 제약을 충돌 판정 근거로 삼아 정규화된 삼방향(set-algebra) RDF 병합을 수행하고, 이를 실제 저장소에 구현해 합의된 기준(벤치마크·레플레이)으로 평가하여 인간 개입을 줄이는 실용적 효과를 보였다.

## 해결하려는 문제

직렬화 기반의 라인 머지는 그래프의 비순서성 때문에 불필요한 텍스트 충돌을 만들고, 반대로 스키마가 명시적으로 경쟁을 규정하는 경우(예: sh:maxCount)에는 서로 다른 값들을 조용히 공존시켜 진정한 의미상의 충돌을 놓친다. 연구 질문은 충돌 판정을 데이터 모델이 이미 정의한 산출물인 스키마(SHACL)에서 직접 파생하면 병합에서 어떠한 이득(질적·양적)이 있는지, 실제 배포 경로에서 구현 가능한지, 그리고 어떤 한계가 남는지를 검증하는 것이다.

## 핵심 기여

- SHACL의 cardinality(예: sh:maxCount)를 충돌 판정(predicate)으로 사용하는 정규화된 삼방향 병합 연산자 구현 및 Quipu 저장소에의 실제 배포(share_merge, 약 480줄 Rust).
- 재현 가능한 합의형(oracle) 합류 벤치마크(합성 시나리오, 5개 시드)와 동일 분류 회계(contract)를 통한 8개 전략 비교(본 논문과 레퍼런스 구현 포함).
- 운영 환경에서 기록된 분기 사건(replay) 코퍼스를 이용한 평가(105개의 수리(수정) 사건 중 93으로 축소, 939 건의 중복-값 사건 재현)로 합성 실험의盲点 재현 및 실무적 이득 정량화.
- 스키마(쉐이프) 선언의 진화 케이스 연구: 먼저 쉐이프를 병합한 뒤 데이터 병합 시나리오를 통해 cardinality 변화는 처리되나 데이터타입 변화는 충돌 탐지의盲点으로 남고 후-검증으로 잡힌다는 관찰.
- 스키마를 읽지 않는 오라클(또는 대체 판정자)과의 비교·재판정 실험을 포함해, 잘못된(누락·과도한) 쉐이프가 병합 품질에 미치는 영향과 비대칭적 위험을 보고.

## 접근 방법

* 세 부분으로 구성된다.
* (1) 트리플을 RDFC-1.0 기반 정규화(정규 레이블링)된 canonical triple 집합으로 취급하여 삼방향 병합을 집합 대수로 수행한다.
* (2) 병합 단위는 (subject, predicate) 슬롯으로 정의하고, 각 슬롯의 기저값·ours·theirs에서 계산된 M[s,p]값의 크기가 쉐이프 S가 선언한 maxS(s,p) (없으면 ∞)를 초과하면 해당 슬롯을 'contended'로 판단하여 충돌로 기록하고 병합을 중단한다.
* 구체적 충돌 클래스는 functional divergence(단수 바운드에서 서로 다른 두 값), cardinality overflow(n>1 바운드 초과), delete/modify(한쪽이 삭제하고 다른 쪽이 교체한 경우)로 보고된다.
* (3) 충돌이 없을 때는 Gm = (Go ∪ Gt) \ (Ro ∪ Rt)로 결과를 만든 후 동일한 shapes graph로 후(후속) SHACL 검증을 수행해 설계 주장(카디널리티에서 유래한 충돌은 자동 병합으로 제시되지 않음)이 입증되는지 확인한다.
* 구현 세부사항: 쉐이프는 병합 대상 번들(bundle)에서 읽고 충돌 레코드는 슬롯별 증거(기저·ours·theirs 집합, 선언된 maxCount)를 포함한다.

## 주요 결과

- 합성 벤치마크(Arm A): 5개 시드(1,7,42,99,2026), 각 시드 200 엔티티, 각 측면 200 편집(총 400), overlap 0.5에서 oracle은 총 54개 충돌(그중 21개 alias-mint로 트리플 수준에서 보이지 않음) 생성. 트리플 수준에서 보이는 33개 충돌에 대해 shape-aware 연산자는 정확히 33개의 결정을 제기(시드별 일치)하고 거짓 긍정 0, 잃은 트리플 0, 위조 트리플 0, SHACL 위반 0을 보고(precision 1.000). 같은 33개를 context-merge(재구현)도 검출했으나 슬롯 단위로는 총 845개의 질문을 제기(즉 동일 검출을 더 많은 인간결정으로 유도).
- 합성 벤치마크 자세한 분류: shape-aware의 33결정은 13 functional divergence, 10 cardinality overflow(어떤 술어는 maxCount=4), 10 delete/modify로 구성(Table 3).
- 레플레이(운영 기록 기반, Arm B): 기록에서 추출한 105개 사람의 alias 수리(12 chained pairs 제외 후 93) 중 operator는 0/93 검출(트리플 수준 연산의 불가피한 한계). 반면 comment-double 사건(상품화 경로의 append 오류로 동일 predicate가 중복 삽입된 경우) 939건은 shape-aware가 모두 충돌로 보고하여 인간 결정을 요구함(재연에서 939 결정).
- 스키마 진화 실험(Arm E): maxCount 조정(팽창/수축)은 병합 순서(쉐이프 먼저 병합)로 의도한 대로 처리되지만, 데이터타입 변경(예: string→integer)은 카디널리티 기반 탐지기가 놓치고 후-병합 SHACL 검증이 이를 포착하여 거부함(table 7).
- 오라클 비의존 검사(Arm F): 쉐이프를 읽지 않는 독립 오라클의 24개 단일-슬롯 케이스 중 셰어 병합 경로가 도달 가능한 케이스에 대해 사실·히스토리 일치(share_merge: 19 일치 + 4 trace 차이, fork_promote: 22 일치) — 즉 코드 경로가 오라클 기대와 일관된 사실·이력 출력을 생산함.

## 한계

- 저자가 명시한 한계: 주장은 좁게 한정되어 있다 — 슬롯 수준의 카디널리티 충돌에 대해서만 '더 적은 인간 결정으로, 데이터 손실 없이'를 지원하며 일반적인 병합 정합성(모든 SHACL 제약, 데이터타입, 빈 노드, 리스트 구조, 엔티티 동형성 등)은 다루지 않음(§9).
- 저자가 명시한 한계: alias divergence(서로 다른 이름을 같은 엔티티에 발행)는 트리플 수준 연산으로는 불가시적이며 논문 실험에서도 0/93 검출로 측정된 명확한 한계(무슨 스키마도 이를 고치지 못함).
- 저자가 명시한 한계: 벤치마크 입력은 ground graphs(빈 노드 없음)만 사용하므로 RDFC-1.0 기반의 빈 노드 정규화는 벤치마크에서 검증되지 않음.
- 실험·분석에서 드러나는 제약: 충돌이 발생하면 전체 병합을 차단하고 아무 것도 쓰지 않는 보수적 전략을 택함 — 부분 적용(비쟁점 슬롯은 적용하고 쟁점 슬롯만 보류)은 미래 작업으로 남음(사용성 비용). 또한 스키마를 번들에서 읽기 때문에 잘못된(누락된) 바운드는 데이터가 조용히 손실되는 결과를 초래할 수 있음(실험에서 관찰됨).

## 개발자 관점

- 재현: 구현 및 벤치마크·레플레이 아티팩트는 개발 리포지토리(논문에 명시된 github.com/intigraph/quipu)와 벤치마크 명령으로 재생산 가능하다고 본문에서 밝힘(예: bench merge, cargo run --example replay).
- 구현: 연산자는 canonical triple 집합 위에서 집합 대수로 동작하므로 직렬화 독립성 확보(RDFC-1.0 기반). 단, 본 논문 벤치마크는 빈 노드를 포함하지 않으므로 빈 노드 canonicalization은 별도 검증 필요.
- 배포/운영: 쉐이프는 번들에 포함된 것을 읽어 병합 시점의 계약으로 사용하므로, 분산된 피어들이 각자 다른 쉐이프를 들고 올 수 있고 이 경우 병합 결과·질에 직접 영향을 미친다 — 스키마 유효성·일관성 관리가 운영 위험 요인.
- 비용·도구 통합: 충돌 판정은 슬롯 단위로 증거(기저·ours·theirs 집합)를 포함한 DecisionRecord를 생성하여 사람이 효율적으로 검토하게 하였고, 이는 UI·검토 워크플로우 설계 시 유용(문제 위치와 이유가 명시됨).
- 안전성: shape-aware는 카디널리티 기반 충돌을 묵인하지 않아 데이터 손실을 방지하지만, 누락된 바운드(잘못된 스키마)는 조용한 데이터 손실을 초래할 수 있어 스키마 품질·배포 절차와 후-검증(merge 후 SHACL validation)을 반드시 설계에 포함해야 함.

**근거 범위:** 이 분석은 제출된 논문 PDF 본문 전체를 근거로 작성했다. 모든 수치·결과·설계 설명은 본문 표와 절(§3–§9)에서 직접 추출하였으며, 외부 코드 저장소나 실행 결과는 논문 본문에서 명시된 기술을 근거로만 언급했다. 벤치마크는 ground graphs(빈 노드 없음)로 구성된 점, 구현이 Rust로 약 480줄이라는 점, 그리고 일부 비용·사용성 세부(예: Jev 실험의 리스트-가격 소계)는 본문 서술에 따른 것이며 본 분석에서 임의 수치나 미확인 구현 세부는 만들지 않았다.
