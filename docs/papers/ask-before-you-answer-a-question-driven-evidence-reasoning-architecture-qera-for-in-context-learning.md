## 한 문장 요약

사용자 대화·기록 같은 실세계 컨텍스트에서 요청과 실제 평가(루브릭) 불일치를 관찰하고, 요청을 체크리스트와 질문들로 변환해 증거를 확인한 뒤 답하는 QERA라는 질문-구동 증거 추론 아키텍처를 제안하여 인-컨텍스트 학습 성능을 향상시킨다.

## 해결하려는 문제

실세계 사용자 컨텍스트(그룹 채팅, 활동 로그, 수정 기록 등)에 대해 LLM에게 추론을 맡길 때 최종 사용자의 요청(request)이 채점 기준(루브릭)을 충분히 규정하지 못하는 경우가 많다. CL-bench Life 벤치마크에서는 루브릭의 80% 이상이 최종 요청과 내용어 기준으로 60% 미만만 겹치며(즉 요청이 명세가 아님), LLM이 바로 답할 때 암묵적(implicit) 루브릭에 대해 낮은 통과율(67%)을 보이는 반면 명시적 루브릭에는 81%를 보인다. 기존의 '바로 답하기' 접근은 이런 요청↔평가 불일치에 취약하고, 명시되지 않은 정보요구를 탐지·검증하지 못한다. 연구 질문은(1) 요청을 요구사항(checklist)과 정보유형(typed information needs)으로 변환해 질문을 먼저 던지면 암묵적 루브릭에 대한 성능을 개선할 수 있는가, (2) 코드 기반 필터링과 인용(quote) 검증을 결합한 질문-검증 루프가 유의미한 개선을 만드는가이다.

## 핵심 기여

- QERA(Question-driven Evidence Reasoning Architecture) 제안: 요청을 요구사항 체크리스트와 타입화된 정보요구로 변환하고, 대화 전체에서 답을 도출한 뒤 동일 질문을 인용 검증과 함께 재질문하고 보호된(local) 수정을 적용하는 파이프라인을 제시함.
- 학습이 필요 없는 추론 시 아키텍처로서 설계되어 태스크당 약 4회의 LLM 호출로 동작하도록 구현 및 평가함.
- CL-bench Life(405개 태스크)에 대해 4개의 최신 LLM에서 일관되게 기존 추론-시점 베이스라인과 직답(direct answering)을 능가하는 성능(평균 해결률 21.0%)을 보였음을 보고함(강한 베이스라인 18.2%, 직답 14.6%).
- 요청-기반 질문과 고정된 답변 프로토콜의 기여도를 확인한 절단(ablation) 실험: 고정 답변 프로토콜이 +3.8 루브릭 포인트, 요청-특이적 질문이 +1.6 포인트의 이득을 제공함을 보고함.
- 토큰 효율성 주장: PSCI보다 적은 토큰을 사용하고 Ctx2Skill의 4–5% 수준의 토큰만 사용하면서도 성능 이득을 냈다고 보고함.

## 접근 방법

* QERA는 다음 단계로 동작한다.
* (1) 요청을 받아 코드 기반 필터링을 통해 사용자의 문장에 충실한 요구사항 체크리스트와 타입화된 정보 필요 항목들로 변환한다.
* (2) 대화 전체(context)에서 해당 질문들에 대해 답을 생성한다.
* (3) 동일한 질문들을 인용(quote)을 포함해 다시 묻고, 이 인용들을 코드로 검증하여 근거(evidence)를 확인한다.
* (4) 검증 결과에 기초한 'guarded local repair'를 적용해 최종 답변을 산출한다.
* 파이프라인은 학습 단계를 요구하지 않으며, 평균적으로 태스크당 약 4회의 LLM 호출을 사용한다.
* 코드 모듈은 (a) 요청→체크리스트 변환의 충실성 검사, (b) 인용 검증을 담당하며, 이들로 질문의 faithfulness와 인용의 정확성을 보장한다.

## 주요 결과

- 데이터셋: CL-bench Life, 총 405개 태스크에서 평가.
- 비교 대상: 직접 답변(direct answering)과 세 가지 추론-시점(inference-time) 베이스라인(요약된 하나는 가장 강한 베이스라인 수치 제공).
- 주요 정량 결과: QERA는 모든 4개 프론티어 LLM에 대해 가장 높은 해결률을 보였고, 평균 해결률은 21.0%이었다. 가장 강한 베이스라인의 평균은 18.2%, 직접 답변은 14.6%였다.
- 루브릭 불일치 관련 결과: 벤치마크에서 80% 이상 루브릭이 최종 요청과 내용어 기준으로 60% 미만만 겹쳤고, LLM이 바로 답할 때 암묵적 루브릭의 통과율은 67%로 명시적 루브릭의 81%보다 낮았다. QERA의 개선은 암묵적 루브릭에서 뚜렷하게 집중되어 있음.
- 호출/토큰 비용: QERA는 태스크당 약 4회의 LLM 호출을 사용하며, PSCI보다 적은 토큰을 사용하고 Ctx2Skill의 약 4–5% 수준의 토큰만 사용했다고 보고함(정량적 토큰 수는 본문에서 직접 명시되지 않음).

## 한계

- 저자가 명시한 한계: 제공된 본문(초록)에서는 저자가 직접 기술한 추가적인 한계 설명은 포함되어 있지 않음.
- 실험적·범위상 제약(본문에서 합리적으로 확인되는 한계): (a) 평가가 CL-bench Life의 405개 태스크에 한정되어 있어 다른 유형의 컨텍스트(예: 다른 도메인별 로그, 더 긴 문서 등)로의 일반화가 본문만으로는 확인되지 않음, (b) QERA는 코드 기반의 필터링·인용 검증 모듈에 의존하므로 코드 실행 환경과 검증 로직의 구현에 민감하며 해당 환경이 없으면 동일한 절차를 재현하기 어렵다, (c) 평균적으로 태스크당 약 4회의 LLM 호출을 사용하므로 호출 수와 지연(latency)이 직답보다는 높을 가능성이 있으며 실제 배포 시 응답시간/비용-트레이드오프가 존재함, (d) 토큰 효율성 비교는 PSCI·Ctx2Skill 대비 유리하다고 보고되나 본문에는 절대 토큰 수나 비용 비교의 세부값이 제시되어 있지 않아 실무 비용 평가에는 추가 정보가 필요함.

## 개발자 관점

- 재현: 재현하려면 CL-bench Life 데이터와 동일한 평가 파이프라인 및 네 개의 프론티어 LLM(저자들이 사용한 LLM 목록은 본문에 상세히 기술되어 있지 않으므로 동일 모델을 쓰려면 원문/부록 확인 필요)이 필요하다. 핵심은 요청→체크리스트 변환, 질문 생성, 코드 기반 충실성·인용 검증, guarded local repair의 구현이다.
- 구현: 코드 모듈은 요청 문장과 체크리스트 간 충실성 판단과 인용(quote) 유효성 검증을 자동으로 수행해야 하며, 이를 위해 안정적이고 안전한 샌드박스 환경에서의 코드 실행이 요구된다. 프롬프트 설계가 성능에 민감하므로 질문 타입화와 고정된 답변 프로토콜을 정확히 재현해야 한다(저자 절단 실험에서 고정 프로토콜이 큰 기여를 함).
- 배포·비용: 태스크당 약 4회의 LLM 호출은 직답보다 더 많은 호출 수를 요구하므로 대규모 배포 시 호출 횟수·지연·비용 추적이 필요하다. 다만 저자 주장대로 토큰 사용량은 일부 비교 대상보다 훨씬 적으므로 토큰 비용 측면에서는 유리할 수 있다. 실제 비용 산정은 사용 모델의 호출·토큰 단가를 반영해야 한다.
- 안전성·검증: 인용 검증과 코드 기반 필터링은 응답의 근거(faithfulness)를 높이는 장점이 있으나, 코드 실행에 따른 보안·격리 문제와 검증 로직의 결함이 잘못된 근거를 허용할 수 있으므로 검증 로직과 샌드박스 보안이 중요하다.
- 추가 연구·확장: 다른 도메인과 더 긴 컨텍스트에 대한 일반화 테스트, 검증 모듈 없이 순수 언어 기반으로 유사한 개선을 얻을 수 있는지, 또는 더 적은 호출로 비슷한 효과를 얻는 비용-효율적 변형을 실험해볼 가치가 있다.
