## 한 문장 요약

AIChipBench는 정수 연산 오라클로 각 디코딩 거래의 출력과 커밋된 상태를 고정하여 LLM 코딩 에이전트가 양자화된 언어모델 디코더용 RTL 하드웨어를 작성·디버그·합성하고, 상태 관련 결함을 드러내는 피드백과 보이지 않는 최종 테스트로 정확성과 PPA(성능/면적)를 평가하는 벤치마크다.

## 해결하려는 문제

하드웨어 언어모델 디코더는 거래 사이에 '영속적 상태'를 유지하므로 잘못된 상태 업데이트가 즉시 출력에 드러나지 않고 이후 수 단계에서야 출력이 망가질 수 있다. 이로 인해 출력만 검사하는 공개 테스트로는 상태 결함을 잡기 어렵고, 에이전트가 한정된 시간과 도구 호출 예산 내에서 문제의 원인을 찾아 고치기 어렵다. 연구 질문은 (1) LLM 코딩 에이전트가 상태 결함까지 올바르게 설계하려면 어떤 디버깅 피드백이 필요한가, (2) 제출된 설계의 ‘최종 정확성’을 어떻게 신뢰성 있게 판정해야 하는가, 그리고 (3) 올바른 설계를 거의 고정 면적에서 가속화하는 최적화 과정이 정확성에 미치는 영향은 무엇인가이다.

## 핵심 기여

- AIChipBench 벤치마크 설계: 정수 연산 오라클로 각 거래(transaction)에서 기대되는 출력과 커밋된 상태(state word)를 고정하고, 공개 테스트·보호된 보류(held-out) 테스트·합성·로컬 검사 등 다중 게이트로 제출을 판정하는 평가 파이프라인을 제시함 (섹션 2).
- 피드백 비교 실험(매치드 스터디): 공개 피드백을 output-only, coarse-state(상태 불일치 플래그), full-state(첫 불일치 상태 단어의 위치)로 분리해 동일 인스턴스에서 비교하고, 상태 위치를 알려주는 피드백이 수락률과 비용에 미치는 영향을 정량적으로 증명함(전체 12 agent–task 셀에서 25.0–46.9pp 향상, 에이전트 시간/수락 설계 13.4→6.5시간).
- 대규모 에이전트 평가: MathCode 허니스를 통해 Sol 5.6, Astra 6, Opus 5.5, Fable 5.1 네 에이전트의 총 9,136 시도(정확성·PPA 트랙 포함)를 실행해 신뢰성과 비용·성능을 비교하고 종합 점수(Score = 100 * ¯c * ¯q)를 제안함.
- 설계·검증 통찰: 공개 테스트를 모두 통과해도 동결(frozen) 제출물이 보류 테스트·리셋·메모리 정체(stall)·합성 등 보완 조건에서 실패하는 사례(예: 148 설계가 공개 테스트 통과 후 최종 불합격; 동결된 69 accepted 중 45개가 32단계 이내 새로운 시퀀스·조건에서 실패)를 제시하여 최종 검사의 중요성을 강조함.

## 접근 방법

* 구성 요소 및 절차 요약: (1) 문제 설정: 각 디코딩 단계는 정수 계약 Fq로 기술되며, 상태 st(예: GDN recurrent state, conv state, attention K/V 캐시, 제어 메타데이터)의 각 정수(=state word)를 오라클이 거래 단위로 고정한다.
* (2) 에이전트-도구 루프: LLM 코딩 에이전트는 샌드박스 워크스페이스에서 파일을 읽고 RTL을 편집하며 lint·컴파일·시뮬레이션·합성 도구를 호출한다.
* 시도(attempt)는 시간·도구 호출·출력 토큰에 상한이 있다(예: Qwen3.5-0.8B scaffold adaptation의 경우 12h/420 tool calls/260k tokens).
* (3) 공개 테스트와 피드백 모드: 공개 테스트는 연산/레이어 단위부터 다단계 디코딩까지 포함하고, 에이전트에게 반환되는 피드백은 설정에 따라 출력 미스매치만(output-only), 상태 불일치 플래그(coarse-state), 또는 첫 불일치 state word의 위치를 포함한 full-state로 달라진다.
* (4) 제출·동결·평가: 제출 시 RTL 해시·동결 후 격리된 평가기로 전송되어 다섯 게이트(Iintegrity, Ipublic, Iheldout, Isynth, Ilocal)를 모두 통과해야 accepted(Y=1)가 된다.
* Iheldout은 신규 가중치·토큰 시퀀스·비영(非0) 캐시 위치·리셋 후 활동·메모리 스톨·파라미터 재로드 등 조건을 포함한다.
* (5) PPA 트랙: 에이전트는 정답(참고) 설계에서 시작해 throughput을 ≥5% 향상시키고 LUT 증가를 ≤2%로 억제하는 개선을 목표로 한다.
* 물리적 구현은 Vivado 2024.1과 AMD Alveo U250 FPGA를 사용해 place-and-route 및 보드 전력 측정을 수행한다.

## 주요 결과

- 시도 규모: 네 에이전트가 총 9,136 시도(정확성 트랙과 PPA 트랙 합산)를 수행함(섹션 3 및 부록 표).
- 종합 점수: Score = 100 * ¯c * ¯q로 계산했을 때 Fable 5.1 = 25.02, Sol 5.6 = 24.53, Astra 6 = 16.78, Opus 5.5 = 16.51(그림 2).
- 정확성 트랙: 수락률(accepted over attempts) 중앙값/요약 — Sol 5.6: 61.2% accepted, Opus 5.5: 55.9%, Astra 6: 49.8%, Fable 5.1: 48.3%; 에이전트당 accepted 설계 하나당 비용은 23.9–31.4 agent-hours(부록 테이블).
- 피드백 효과(매치드 스터디): nano T2, T3, Qwen3.5-0.8B의 384 시도 블록에서 output-only/coarse-state/full-state별로 각각 144, 208, 295의 수락을 관찰했고(384 분모 기준), full-state 피드백은 output-only 대비 모든 12 agent–task 셀에서 수락률을 25.0–46.9 percentage points 상승시켰다. 에이전트 시간/수락 설계는 13.4시간→6.5시간으로 절반 수준(비율 0.49 [0.42,0.56]).
- 공개 테스트 한계: 148개의 에이전트 제작 설계가 공개 테스트를 모두 통과하고 최종 평가에서 실패했으며, 동결 제출물 재평가에서 69 accepted 중 45개가 원래 테스트가 요구한 32단계 이내에 새 시퀀스·조건에서 실패함(섹션 4.3). 이들 중 일부(예: 17/85 sequences)는 출력 불일치 대신 저장된 상태만 달랐음.

## 한계

- 저자가 명시한 한계: (i) 실험은 에이전트와 허니스(harness, MathCode)를 함께 평가하므로 결과는 모델 자체뿐 아니라 도구 사용 정책·토큰 예산·테스트 구성에 의존한다(섹션 1, 2). (ii) 목표 정수 계약의 '충실도(fidelity)'는 워크로드에 따라 다르며, 예컨대 Qwen3.5-nano는 FP32와의 top-1 일치가 97.22%로 99% 문턱을 밑돌지만 비용·크기 때문에 유지되었다(섹션 2.3). (iii) 일부 참조(예: Qwen3.6-27B)는 통합 레벨에서 공용/보류 테스트 실패를 보여 추가 개정이 필요하며, 따라서 모든 디코더에 즉시 일반화할 수 없음(섹션 3.3, 부록 F).

## 개발자 관점

- 디버깅 피드백 설계: 하드웨어 에이전트에게는 출력 불일치뿐 아니라 '첫 번째 상태 불일치의 위치'를 제공하는 것이 중요하다 — 위치를 알려주는 피드백은 수락률을 크게 올리고(25–46.9 pp) 에이전트 비용을 절반가량 줄임(섹션 4.2).
- 견고한 최종 검증: 공개 개발 테스트만 통과시켜서는 안 되며, 동결된 제출물에 대해 보류된(held-out) 시퀀스·리셋-후-활동·비영(非0) 캐시 위치·메모리 스톨 등을 포함한 더 힘든 최종 검사를 반드시 수행해야 함(섹션 2.1, 4.3).
- 스캐폴드 활용 권장: 동일 작업을 스캐폴드에서 시작하면 인터페이스에서 처음부터 만드는 것보다 수락률이 현저히 높음(예: Gemma3 4B, Llama3.2-1B 등에서 두 시작 방식 비교 결과; 섹션 4.1, 표 5).
- PPA 최적화의 위험 관리: 성능·면적 최적화 과정은 정확성을 깨뜨리기 쉬움 — PPA 시도 중 '정확성 유지 실패' 사례가 다수 존재하므로 최적화 루프에 엄격한 정합 검사(정밀 보류 테스트, 합성 및 라우팅 후 재검사)를 배치해야 함(섹션 3.2, 4).
- 인프라 및 비용 계획: 큰 참조 설계의 한 번의 검증·합성(예: 0.8B 참조의 클린 패스는 162분)이 매우 비용이 크므로 예산(시간·도구 호출)과 시뮬레이션·합성 비용을 고려한 시도 설계가 필요함(섹션 2.1, 2.2).
