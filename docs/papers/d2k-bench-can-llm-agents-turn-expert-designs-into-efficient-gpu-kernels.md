## 한 문장 요약

LLM 에이전트가 전문가 설계 지침(L1/L2/L3)을 실제 Triton 커널 구현으로 얼마나 잘 번역하는지 진단하는 D2K-BENCH(26개 과제·85개 워크로드)와 쌍대(지침 유무) 평가 프로토콜·LLM 판정자를 제안하고, 다섯 모델에서 지침의 이점과 남은 한계를 정량적으로 분석한다.

## 해결하려는 문제

LLM 기반 에이전트가 자동으로 GPU 커널을 생성하더라도 실행 시간만으로는 전문가 설계(알고리즘 변환, 데이터플로우, 저수준 최적화)가 실제 구현에 의해 얼마만큼 보존되는지 구별할 수 없다. 논문은 '설계를 발견하는 능력'과 '발견된 설계를 코드로 구현·튜닝하는 능력'을 분리해 진단하고, 전문가 지침이 에이전트의 성능 향상에 기여하는 정도와 어떤 설계 속성이 구현되지 못하는지를 규명하려고 한다.

## 핵심 기여

- 26개 과제와 85개 워크로드로 구성된 진단형 벤치마크 D2K-BENCH를 구성하고, 각 과제에 대해 L1(알고리즘 인사이트)·L2(데이터플로우)·L3(저수준 최적화)로 체계화된 전문가 설계 지침과 레벨간 의존성을 기록함(Section 2).
- 쌍대 평가 프로토콜을 설계함: 동일한 작업 기술서·워크로드·툴·하드웨어·350턴 예산을 두고 '지침 있음/없음'으로 각각 에이전트를 실행하고, 실행 시간 기반 성능 점수(Sperf)와 런타임을 숨긴 LLM 판정자(JSdesign, JSimpl)를 결합해 설계 발견과 구현 완성도를 분리해 진단함(Section 3).
- 독립 설계 제안과 생성된 실행 소스에 대해 LLM 판정자를 사용해 L1/L2/L3 수준에서 코드 근거(evidence)를 요구하는 평가를 도입하고, 이 판정 점수와 측정된 성능의 정렬성을 분석함(Section 3.3, 4.2).
- NVIDIA B200 환경에서 다섯 모델(GPT-6-Astra, Claude-Opus-4.8, GPT-5.6-Sol, GLM-5.3, Kimi-K3)을 대상으로 지침의 효과를 정량화하고, 지침으로 인해 Correctness·Sperf·구현 점수(JSimpl)가 향상되었음을 보고하며 동시에 남은 구현 단점을 식별함(Section 4).
- 벤치마크, 입력·평가 파이프라인, 판정자 프롬프트 등을 포함한 코드와 자료를 공개함(코드 링크 제공).

## 접근 방법

* D2K-BENCH는 각 과제마다 공유된 작업 파일(작업 설명, 워크로드 정의, 입력 생성기, PyTorch 레퍼런스, 구현 요구사항, 빈 solution.py 템플릿)을 제공한다.
* 실험은 두 가지 입력 구성(지침 없음 vs 지침 있음)을 쌍으로 실행한다.
* 지침은 L1(알고리즘), L2(데이터플로우), L3(저수준 최적화)로 구조화되고 레벨간 의존성을 기록한다.
* 에이전트는 MCP(read/write, bash, submit 등) 도구를 통해 반복적으로 커널을 구현·컴파일·프로파일·제출하며 최대 350턴을 사용한다.
* 제출물은 정적 검사(AST, 링크 검사 등)로 '커스텀 Triton 커널 사용' 등 구현 요구사항을 검증하고, CUDA 이벤트/그래프를 통한 타이밍 측정으로 지연을 재고한다.
* 성능 점수 Sperf는 과제별로 Fable-5의 첫 올바른 제출(unguided baseline)의 지연을 분모로 하는 기하평균 속도비를 사용(부적합 시 0.5 페널티).
* 독립 설계(JSdesign)와 생성 코드(JSimpl)는 Qwen3.8-Max-0902 판정자가 L1~L3 각각 0–100(다섯 앵커)로 평가하며, JSimpl은 각 레벨 점수의 산술평균이다.
* 판정자는 실행시간을 볼 수 없고, 코드 근거(1–4개 인용)를 요구한다(Section 3).

## 주요 결과

- 데이터셋/환경: 26개 과제, 85개 워크로드, NVIDIA B200(8 GPU) 환경, Triton 구현 언어, 350턴 예산(Section 2, A.2).
- 정확성 개선: 130개의 모델–과제 페어에서 정답률이 93.1%에서 98.5%로 상승(Section 4.1, Table 1).
- 종합 성능(Sperf): 모델별 Sperf의 전체(26개 과제 기하평균)를 계산한 결과, 전체 평균 Sperf가 지침 없을 때 1.46에서 지침 있을 때 1.95로 증가(약 33.9% 상승)(Section 4.1, Table 1).
- 완전 정답 모델의 속도향상: GPT-6-Astra·Claude-Opus-4.8·GPT-5.6-Sol 세 모델(각각 26개 과제에서 올바른 제출 보유)에 대해 기하평균 속도비가 1.69×(무지침)에서 2.49×(지침)로 증가함(Section 4.1, A.3, Table 4).
- 구현 점수(JSimpl): 다섯 모델 평균의 결합 구현 점수(세 레벨 평균)가 무지침에서 57/100에서 지침에서 70/100으로 상승(Section 4.1, Table 2). 구현 판정 점수는 실행시간 없이도 성능 순서 및 지침에 따른 향상 방향을 대략 포착함(Section 4.2, Table 2).

## 한계

- 저자 명시(논문 본문): SOL(속도-오브-라이트) 점수는 D2K-BENCH의 알고리즘·데이터플로우 변경으로 인해 PyTorch 기준에서 유도된 하한이 더 이상 유효하지 않아 보고하지 않음(Section 3.2).
- 저자 명시(논문 본문): LLM 판정자(JSimpl, JSdesign)는 런타임을 보지 않는 '런타임-블라인드' 평가로 근사적 정렬성만 보이며 완전 동등성을 보장하지 않음(Section 4.2).
- 실험 범위 제약(본문에서 확인되는 제약): 평가한 모델은 다섯 모델에 한정되고(human-selected), 하드웨어는 NVIDIA B200으로 단일화되어 있어 결과의 일반화는 제한적임(Section 4, A.2).
- 실험적 관찰(본문): 지침은 성능과 정확성을 개선했지만 '평가된 설계 속성' 중 일부는 여전히 구현되지 않음—즉, 설계 발견의 이점이 구현으로 완전 전이되지 않는 경우가 존재함(결론 및 섹션 4).

## 개발자 관점

- 지침 구조화(L1/L2/L3)와 레벨간 의존성 명시가 실무적 가이드로 유효: 평균적으로 L1(알고리즘) 지침이 가장 큰 단일 기여를 하고, L2/L3가 추가적 이득을 줌(Section 4.3, Figure 3). 따라서 자동화 파이프라인에선 알고리즘적 변환을 우선 제공하고 데이터플로우·저수준 지침을 순차적으로 보강하는 것이 효율적이다.
- 평가 파이프라인 구현 시 정적/런타임 검증 병행 필요: 구현 요구사항 위반(예: 기존 구현 호출 금지)을 AST·링크 검사로 자동 검출했고, 타이밍은 CUDA 이벤트/그래프로 일관되게 측정함(Section 3.1–3.2). 재현하려면 Triton, CUDA 툴체인, Nsight 등 동일한 도구·하드웨어 스택이 필요하다(A.2).
- LLM 판정자 기반의 코드 증거 요구는 '코드에 설계 근거를 명시적으로 드러내기'를 요구함: 판정자는 각 레벨 점수마다 1–4개의 실행 가능한 소스 인용을 필수로 요구하므로(Section 3.3, C.1), 자동 생성 코드가 설계 의도를 실행 가능한 코드 패턴(예: 재시작 경계, 상태 소유권, 삼각 계산·대칭 복사 등)으로 드러내지 않으면 낮은 점수를 받는다.
- 비용·운영 고려: 전문가 지침을 추가하면 토큰 사용량과 API 비용이 늘어남(예: Claude-Opus-4.8 실험에서 전체 토큰·비용이 29.9% 증가, 캐시 읽기 토큰이 크게 증가함; A.4, Table 6). 대규모 자동화에서는 지침 전송과 캐시 전략의 비용을 평가해야 한다.
- 디버깅·튜닝 루프 설계: 에이전트는 프로파일(예: ncu)·정적 검사·실행 피드백을 사용해 반복적으로 수정하므로, 재현 구현은 동일한 도구 체인과 명확한 '최종 제출 선정 기준(정확성·모든 워크로드 타이밍)'을 포함해야 함(Section 3.1).
