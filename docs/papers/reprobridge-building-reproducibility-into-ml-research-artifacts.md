## 한 문장 요약

논문은 ReproBridge라는 에이전트 중심 워크플로와 표준화된 '정제된 재현성 아티팩트(RRA)'(정제 코드베이스, 환경 설정, 실행 런처, 재현 가이드)를 제안해, 재현 과정에서 회복한 절차·결정을 보존하면 이후 독립적 재현 성공률과 비용 효율이 개선되는지 실험적으로 입증한다.

## 해결하려는 문제

기존 연구에서는 논문과 공개 코드에 흩어진 불명확한 설정·종속성·출력 매핑 때문에 실험 재현에 많은 수작업 복원이 필요하다. 코드를 그대로 제공해도 누락된 세부사항을 채우는 재현자의 능력에 결과가 좌우될 수 있다. 본 연구는 ‘회복한 절차와 결정을 보존하면 이후 재현이 더 성공적이고 비용 효율적인가?’라는 구체적 질문을 다룬다.

## 핵심 기여

- 정제된 재현성 아티팩트(RRA)를 네 구성요소(정제 코드베이스, 환경 설정, 실험 런처, 재현 가이드)로 표준화하여 실행 절차와 그 이유를 보존하는 아티팩트 설계 제안(Section 3.2).
- 에이전트 기반 구축 워크플로(ReproBridge): Specify/Execute/Preserve의 세 단계와 역할(Intake, Planner, Builder, Reproducer, Distiller, Packager, Reviewer)을 정의하고, 에이전트가 실행·수정·기록·패키징하도록 설계(Section 3.1, Fig.3, Table 2).
- ReproBridge-Bench 벤치마크 수집 및 평가 인프라: 36개 논문, 387개 실험, 1,029개의 검증된 재현 태스크(각 태스크에 대해 5개의 인간 검증 기준 점수) 구성 및 수치적 호환성 기준 정의(Section 2, Table 1).
- 독립적 실행 무결성 감사를 도입하여 단순 수치 근접만으로 채점하지 않고 실행 증거(스크립트·로그·타임스탬프·해시)를 검증하는 Auditor 프로세스 설계(Section 4.1, 감사 기준 및 판정절차).
- 대규모 실험을 통해 정제 아티팩트가 재현 성공률과 하위 API 비용을 일관되게 개선함을 보이고(다양한 모델·민감도 분석·구성요소 소거 실험 포함), 언제·왜 개선되는지 사례 기반 분석 제공(Section 4, Tables 3–6, D. 사례들).

## 접근 방법

* 본문에 따라 ReproBridge는 사람과 에이전트의 분업으로 동작한다.
* 먼저 Intake/Planner 단계에서 논문·원시 커밋·선택된 태스크를 맵핑하고, 측정 단위를 명시한다.
* Execute 단계에서 Builder가 환경을 준비하고(잠김된 종속성·컨테이너·데이터 스크립트), Reproducer 에이전트가 계획에 따라 실행하여 측정값·코드 변경·재실행 기록·실행 실패 이유를 파일로 남긴다.
* Preserve 단계에서 Distiller가 수정·결정·민감도·변경기록을 정리한 재현 가이드를 생성하고 Packager가 정제 코드·환경 설정(설치 스크립트/컨테이너)/런처 스크립트/가이드를 묶어 RRA를 만든다.
* 후속 Reproducer는 원시 코드(Raw) 또는 RRA를 받아 24시간 제한 내 재현을 시도한다.
* 평가에는 수치적 호환성(5개 인간 검증 관측의 평균과 예측구간; 기본 q=0.95)과 Auditor의 실행 무결성 판정이 결합된다.
* 구성요소 기여도는 컴포넌트 제거(ablation)로 측정하며 외부 벤치(CORE-Bench Hard)와도 비교한다(Section 2–4, Appendix 참조).

## 주요 결과

- 벤치마크: 36개 논문에서 선별·검증된 1,029개 다운스트림 태스크(전체 선별 태스크 1,463개 중 70.3%)를 사용. 각 태스크는 5개의 인간-검증 참조 관측을 가짐(Section 2, Table 1).
- 주요 정량 결과(세 번 평가의 평균): 네 모델(Sonnet 4.6, Sonnet 5, Opus 5, Gemini 3.8 Flash)에서 정제 아티팩트(RRA) 사용 시 평균 재현 성공률이 원시 코드 대비 크게 향상(논문 전반 평균치: Raw 76.4% → RRA 92.6%로 보고; Table 3에 모델별 수치 제시).
- 모델별 핵심 수치(표준편차는 논문 표기): Sonnet 4.6 72.3%→91.6%(+19.3pp), Sonnet 5 76.5%→93.3%(+16.8pp), Opus 5 89.2%→94.7%(+5.5pp), Gemini 3.8 67.6%→90.8%(+23.2pp) (Table 3).
- 하위 비용/토큰 절감: RRA는 평균 API 지출을 모델별로 16.8%–23.7% 절감(예: Sonnet 4.6 USD 3,165→2,512, Sonnet 5 USD 1,726→1,317 등), 토큰 사용도 감소(표 Table 3). 크로스-모델 성공률 격차는 Raw에서 21.6pp에서 RRA로 3.9pp로 축소되어 약한 재현자도 높은 성공률을 달성(Section 4.2, Table 3).
- 외부 비교: CORE-Bench Hard(45 캡슐)에서 RRA는 캡슐 성공률을 Raw 62.2% → RRA 73.3%로 개선하고(SONNET 5가 RRA 구성), 세션 시간 중앙값과 USD/성공도 감소(표 Table 4). Median 시간 33→14.4분, USD/성공 8.43→4.34 등(Section 4.2, Table 4).

## 한계

- 저자가 명시한 한계: RRA 구축 비용(API 사용) 발생 — 36개 아티팩트 구축에 API 비용 총 $5,026(평균 $139.61/논문). 논문은 재사용이 충분히 반복될 때(모델별로 8–13회 전체 재사용) 비용 회수 가능하다고 분석(Section 4.7, E.1).
- 저자가 언급한 감사( Auditor )의 불완전성: 자동 Auditor(Codex, Claude 등)는 완전하지 않아 일부 무결성 위반을 놓칠 수 있고(Auditor별 정밀도·재현성 차이 보고), 최종 판단을 위해 인간 검증이 필요함(Section 4.6, Table 7, human review 결과).
- 본문에서 드러나는 제약(저자가 직접 언급한 것과 구분): 실험 집합은 ICML Spotlight 등에서 코드가 공개된 논문으로 표본화되어 있어 모든 영역·논문 유형에 일반화하기 어렵고(36개 논문에 국한), RRA가 잘못된 선택(예: 보존된 잘못된 설정)을 함께 전승해 일부 Raw→RRA 역전(reversal)을 초래할 수 있음(136건의 역전 사례; Section 4.4, D.3).
- 정량 결과는 평가 규칙(예: 호환성 간격 q 값, 95%/80% 등)과 Auditor 판정에 민감하며, 하드웨어·자원 제약(시간·GPU)으로 인해 일부 태스크는 원천적으로 재현 불가능하거나 비교가 제한됨(Section 2.4, 4.3, D.3).

## 개발자 관점

- 아티팩트는 단순 코드 번들 이상이어야 함: 실행 가능한 '정제 코드' + 정확한 '환경 설치 경로'(종속성 고정·빌드 절차) + '실험 런처'(태스크→설정 연결, 스모크테스트/채점 런처 구분) + '재현 가이드'(모호성, 변경기록, 민감도·반복 규칙) 네 요소를 함께 제공하면 이후 재현자가 많은 수작업을 줄일 수 있음(Section 3.2, Fig.4).
- 환경 복원이 특히 중요: 코드 패치 없이도 호환되는 종속성·빌드 루트를 보존하면 다른 세션에서 즉시 성공하는 사례가 반복됨(WBMM 사례, Section 4.4). 환경·코드 제거 실험에서 성공률 손실이 가장 큼(Table 6).
- 출력-집계 규칙과 측정 단위를 명시하라: 논문과 코드 사이의 미지정·모호한 집계(예: 평균/합/best-of-N 등)를 가이드를 통해 명시하고 수집기를 제공하면 잘못된 집계로 인한 실패를 방지할 수 있음(Mixture of Concept Bottleneck, SCIQL 사례).
- 감사 라인과 증거 보존을 설계하라: 측정값을 산출한 스크립트·로그·출력 파일 해시·타임스탬프를 연결하는 레저를 남기고, 감사자가 실행 무결성을 검증할 수 있도록 하라. 수치 근접만으로는 충분하지 않음(Section 4.1, 4.6).
- 비용-편익 고려: RRA 구축에는 선행 비용이 들지만 동일한 아티팩트를 여러 번(논문 전체 워크로드 기준으로 모델별 8–13회) 재사용하면 API 비용에서 순절감 가능. 따라서 조직적 배포 또는 커뮤니티 공유를 통해 비용을 상쇄하는 전략 권장(Section 4.7, E.1).

**근거 범위:** 이 분석은 제공된 논문 PDF 본문(주요 본문, 표, 그림, 부록 요약 포함)의 텍스트를 근거로 작성되었다. 본문에 명시된 표(Table 1–7, 13 등)와 사례 설명을 인용했으며, 코드·실행 로그·부록의 전체 원문을 직접 실행해 확인하지는 못했다. 구현 세부(예: 정확한 스크립트 내용, 컨테이너 이미지 등)와 PDF에 완전히 포함되지 않은 부가 데이터는 생성하지 않았다.
