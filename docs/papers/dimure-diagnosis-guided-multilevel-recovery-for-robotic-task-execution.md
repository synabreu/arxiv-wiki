## 한 문장 요약

DiMuRe는 단계별 진단(phase-specific diagnosis)과 방법 사전조건을 이용해 기존 프로그램 재사용, 기정의 회복 스킬(geometry 기반 재그립 및 bounded VLA grasping), 또는 MLLM 기반 재계획을 선택·검증하는 다층 복구 프레임워크이며, LIBERO-Disturb 벤치마크로 중간 실행 교란에 대한 복원력을 평가한다.

## 해결하려는 문제

로봇 작업 실행 중 목표 물체 이동·미스그립·수신영역 이동 등 물리적 교란이 발생하면 원래 프로그램의 일부는 유효하지만 다음 동작의 전제조건이 깨져 추가 복구가 필요하다. 기존 접근은 단일 경로(예: 단순 재시도, 느린 모델 기반 재계획 등)에 의존하거나 실패 알람만 제공해 어떤 복구 방법이 현재 상태에 적합한지 판단하지 못한다. 본문은 ‘언제 개입해야 하고, 어떤 복구 수단이 적용 가능하며, 복구 결과로 계속 진행할 수 있는지’를 실행 중 관찰(evidence)과 프로그램 컨텍스트만으로 온라인 결정하는 문제를 다룬다.

## 핵심 기여

- DiMuRe: 단계별 진단과 방법(메소드) 사전조건을 사용해 원래 프로그램 재사용(L1), 기정의 회복 스킬(L2), MLLM 기반 터미널 재계획(L3)을 선택·검증하는 다층 복구 아키텍처를 제시하고 구현함.
- LIBERO-Disturb: 중간(미드) 실행 교란(9종)을 명시적으로 주입하고 교란 적용 여부·물리적 효과·원시 평가를 분리 기록하도록 설계된 벤치마크를 제안함(프로그램 기반 에이전트와 VLA 정책 모두 지원).
- 실험적 검증: Encore 개발 케이스 801건(스케줄된 교란)에 대한 비교에서, Local DiMuRe(L1+L2)가 원래 프로그램 대비 완전 과업 성공률을 58.68%→77.65%로 개선함을 보고함(Full(L1+L2+L3)에서는 81.90%).
- 운영적 설계: 단계별 진단(상태/관계/재관측), 메소드 입장 조건(Pm)/실행(πm)/검증(Vm)으로 구성된 후보 순회·검증 절차와 물리적-스텝 예산(입장 임계값 bmin, 보류 r, 캡 Cmax, 시도 한도 Amax 등)을 명시적으로 도입함.
- 로컬 복구와 터미널 재계획의 비용·성능 균형을 분석하고, 복구 시 검증(local verification)을 통해 복구 시도별 성공 여부를 확인하는 체계를 구현·평가함.

## 접근 방법

* DiMuRe 아키텍처는 (1) 실행 모니터가 모션·그리퍼 호출을 가로채어 그립·플레이스 기록과 객체/수신영역 관측을 유지하고, (2) 규칙 기반 진단기 D(ϕt, Et)가 현재 조작 단계 ϕt(예: grasp, transport, place, verify)와 관측·액션 피드백 Et를 받아 진단 결과 dt(진단 코드, 규칙 신뢰도, 권장 응답, 증거)를 출력한다.
* 진단은 먼저 그리퍼 열기·객체-도구 추종(residual efollow 정의, Eq.2)·릴리즈·플레이스 여부를 검사하고 증거가 불충분하면 재관측을 요청한다.
* 복구는 세 레벨로 계층화된다: L1(원래 프로그램 재사용)에서는 기록된 그립/플레이스 세그먼트를 측정된 객체 중심 차이 δt로 수평 이동하여 재생(Eq.3); L2(기정의 회복 스킬)는 기하 기반 재그립과 GraspVLA 같은 bounded VLA 정책을 기동하고 사전조건·사이즈 한계를 확인하여 실행 후 그립 검증을 수행; L3(터미널 MLLM 재계획)는 원래 프로그램 종료 후 RGB 이미지·상태·프로그램 컨텍스트·이력 피드백을 입력으로 MLLM이 수정 코드(fragment)를 생성하고 실행·검증·반복한다.
* 각 후보 메소드는 Rm=(Pm, πm, Vm)로 표현되어 입장조건(am), 실행(πm), 로컬 검증(vm)을 거쳐 다음 동작(스킵·진행·검증완료 등)을 결정한다(식 5).
* 물리적-스텝 예산 관리는 누적 스텝 nt, 전체 예산 B, 활성 한도 Bt 및 절차별 캡 Cmax, 최소 입장 보유 bmin, 시도 한도 Amax(=3) 등으로 엄격히 회계되며, 터미널 플래너 진입 임계값 bplan_entry=80 및 라운드 연속 임계값 bplan_round=40, Kplan=32 라운드 제한, 각 생성 fragment에 대한 실행 시간 Texec=45s 같은 파라미터로 운영된다.
* 로컬 복구는 템플릿 재생→기하 재그립→VLA 순으로 후보를 고정 순서로 시도하며, 각 시도 후 검증을 통해 성공 시 종료하거나 다음 후보로 진행한다.

## 주요 결과

- 평가 데이터: Encore 개발용 스케줄된 교란 801건(30개 고정 Encore 프로그램 × 3 시드)에서 비교 수행. Original, L1-only, L2-only, Local(L1+L2)는 동일한 native 물리-스텝 허용(1,000)을 사용. Full(L1+L2+L3)은 native 1,000 + terminal 400으로 추가 허용 및 조기 핸드오프를 허용(따라서 Full과 Local 비교는 동일 예산 비교가 아님).
- 완전 과업 성공률(SR): Original 58.68% (470/801), L1-only 73.66% (+14.98 pp), L2-only 65.54% (+6.87 pp), Local (L1+L2) 77.65% (+18.98 pp), Full 81.90% (+23.22 pp) (Table I, II).
- 물리적 스텝 및 시간: 전체 케이스 평균 물리-스텝은 Original 328.90, Local 310.20(더 낮음); 그러나 평균 wall-clock 시간은 Original 4.65s, Local 5.47s(더 김). 성공 케이스 평균은 Original steps 213.46/2.93s, Local 226.89 steps/3.94s(표 II). Full은 추가 허용 때문에 전체 평균 361.30 steps, 19.59s로 실행 비용이 큼.
- 이상 반응(레트로스펙티브 라벨링): 801 케이스 중 161개(20.1%)에 대해 독립적으로 식별 가능한 첫-결함 윈도우가 라벨링되었고, Local/Full 모두 반응 커버리지는 126/161(78.26%). 반응 후 과업 성공률은 Local 94/126(74.60%), Full 101/126(80.16%) (Table II(b)).
- 회수성 기여 분해: L1-only는 grasp-slip 계열에서 강점, L2-only는 object-pose-change 계열에서 더 강세를 보이며, 두 수준을 결합한 Local이 더 큰 이득을 냄(세부 유형별 성공 Table S9). 두 단일 수준이 해결하는 케이스가 서로 보완됨(예: L1-only 전용 성공 106건, L2-only 전용 성공 41건). (Appendix B, Table S9).

## 한계

- 저자 명시 한계: (1) 가림(occlusion) 및 잘못된 객체 매칭이 메소드 선택과 로컬 검증에서 오류를 유발할 수 있음, (2) 고정된 후보 순서로 인해 예산 소진 전에 적절한 VLA나 L3가 시도되지 못할 수 있음, (3) 터미널 재계획 필요를 결정할 더 신뢰성 있는 과업 완료 검사 필요, (4) 인지·기억·추론 구성요소의 기여를 분리하는 추가 소거(ablation) 필요, (5) 저장된 복구 경험은 평가 전 고정되어야 함, (6) 연구 결과는 시뮬레이션에 국한됨.
- 실험·분석에서 확인되는 제약: (a) Full 구성은 추가 물리-스텝 허용(1,400)과 조기 핸드오프를 포함하므로 Local 대비 L3의 기여를 동일 예산에서 분리할 수 없음, (b) 진단 정밀도 평가는 161/801(20.1%)의 ‘감사 가능한’ 윈도우에 한정되어 있으며 전체 집합에 일반화하기 어려움, (c) 일부 성능·시간 비교는 서비스 공유(동일 GPU·서비스)와 비완전한 인터리빙으로 인해 wall-clock 비교가 서술적(descriptive)임, (d) VLA와 Encore의 네이티브 평가 프로토콜이 달라 직접 비교 불가.

## 개발자 관점

- 재현에 필요한 주요 구성요소: Encore 프로그램 집합(30개 고정), 실행 모니터(모션·그리퍼 호출 가로채기), RGB-D 기반 객체/수신영역 추적(Encore 통합 사용), GraspVLA 서비스(논문은 GraspVLA [25] 사용), SAM 3 세그멘테이션 서비스, 터미널 MLLM(논문은 DeepSeek V4.1 Flash 사용) 및 물리-스텝 회계/예산 관리 로직이 필요함(Appendix B 참조).
- 검증·안전성: 각 회복 시도는 로컬 검증(Vm)을 통해 그립/릴리즈 상태를 확인하도록 설계되어야 하며, 잘못된 검증(가림·오브젝트 매칭 오류)에 대비한 관측 재시도와 보수적 입장 규칙(Pm)이 중요함.
- 자원·비용: 터미널 MLLM 비용이 큼(Full에서 180/801 에피소드 진입, 총 1,547 L3 요청 기록; 전체 스케줄 평균 1.93 L3 요청/에피소드 및 기록된 평균 입력 토큰 수 204,421, 출력 토큰 570 — Table S11 참조). 실전 배포 시 모델 호출 비용·지연을 예산에 반영해야 함.
- 설계 권고: 후보 시도 순서(템플릿→기하→VLA)는 경험적으로 유효하지만, 예산·교란 유형·검증 신뢰도에 따라 동적 우선순위(메타 의사결정)를 도입하면 더 나을 수 있음. 또한 터미널 재계획 진입 임계(bplan_entry, bplan_round)와 각 절차의 완료 보류(reserve r, rvla 등)를 엄격히 설정해 실패 시 과도한 자원 소모를 방지해야 함(Appendix A의 파라미터 권고값 사용 가능).
- 평가·로그: 벤치마크는 교란 적용 여부와 실제 물리적 효과를 분리 기록하므로(표 S7), 시스템별 실패 원인·효과 분석을 위해 동일한 분리 로깅을 구현할 것.
