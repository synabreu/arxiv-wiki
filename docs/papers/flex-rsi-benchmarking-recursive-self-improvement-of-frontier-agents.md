## 한 문장 요약

Flex-RSI는 동일한 일반용 '하니스(harness)'와 고정 예산 하에서 실행자(executor)가 해를 개선하고 개선안이 검증(held-out validation)을 통과할 때만 갱신하며, 개선자(improver)가 하니스(실행자·자기 자신 포함)를 재작성하는 반복적 자기개선(Recursive Self-Improvement, RSI)을 측정하는 비전·로보틱스 중심의 벤치마크다.

## 해결하려는 문제

기존 벤치마크들은 보통 모델을 고정된 하니스 안에 넣고 산출물(해, 코드 등)만 채점하거나 대규모 모델 학습을 목표로 한다. 실제 에이전트 배포에서는 프롬프트·도구·메모리·제어 루프 등 하니스 자체가 성능에 결정적이며, 주어진 작업의 피드백만으로 '작동 방식(하니스)'을 개선해 더 좋은 최종 결과를 얻을 수 있는지를, 그리고 어느 정도의 예산 안에서 가능한지를 측정하는 체계적 평가가 부족했다. Flex-RSI는 (1) 작업 해(solution) 자체의 개선과 (2) 해를 만들어내는 과정(하니스)의 개선을 분리해 동일 시작점·고정 예산·개발/검증/테스트 분할 하에서 비교할 수 있는 기준을 제공한다.

## 핵심 기여

- Flex-RSI 벤치마크 제안: 동일한 일반용 시작 하니스와 스타터 솔루션, 개발/검증/테스트 분할, 고정 예산 규칙을 정의하고 24개 작업(비전·추론·로봇 액션·3D 재구성·이미지/비디오 생성·인프라)으로 구성된 평가 스위트를 공개함.
- 실행자(Executor)–개선자(Improver) 반복 루프 규격화: 실행자가 개발 데이터로 후보 해를 생성하고 검증 데이터에서 개선이 통계적 노이즈 마진(δ) 이상일 때만 수용하며, 개선자가 실행자와 자기 자신(하니스)을 수정할 수 있도록 한 구조를 제시함(수용 규칙 및 δ 초기값·조정 가능성 명시).
- 대규모 실험: 18개 전·오픈 모델(11개 closed-source, 7개 open-weight)을 동일한 프로토콜로 24개 작업에 대해 평가하여 자기개선이 어디서·얼마나 효과적인지 분석함.
- 실증적 발견 제시: (i) '해를 직접 구축하는' 작업에서 자기개선 여지가 크고 모델 간 격차가 확대됨, (ii) 연속적 스코어(세분화된 피드백)는 모든 모델에 유리하고 이진 성공/실패 피드백은 특히 오픈-웨이트 모델의 개선을 저해함, (iii) 물리적 안정성·정확성의 엄격한 검사에서는 오픈-웨이트 모델이 더 뒤처짐.
- 하니스 편집의 기여 입증: 페어 실험에서 improver가 하니스 편집을 허용하면 동일 조건 대비 테스트 점수가 개선되는 경우가 대부분(7개 페어 중 6개)임을 보고.

## 접근 방법

* Flex-RSI 프로토콜(본문 기준):
* 자원 및 데이터 분할: 각 작업은 스타터 솔루션 s0, 개발(dev)·검증(val)·테스트(test) 분할, 고정 예산(실행 시간·GPU·모델 호출·검증 평가 횟수·라운드 수 등)을 제공한다.
* 개발분할은 에이전트가 실험과 자체 평가에 사용 가능, 검증과 테스트 분할은 비공개로 유지된다.
* 하니스 구성: H = (E, I).
* 실행자 E는 현재 수용된 해 s_{t-1}을 개발데이터 D_dev만 사용해 편집·실험하여 후보 tilde{s}_t를 만든다.
* 검증 데이터 D_val에서 스코어 S(tilde{s}_t; D_val)가 이전 수용해 s_{t-1}보다 δ 이상 크면 수용하여 s_t = tilde{s}_t, 아니면 s_t = s_{t-1}.
* δ 초기값은 스타터 검증 점수 표준편차의 두 배로 설정되며 improver가 수정 가능.
* 개선자 I는 모든 라운드의 실행 기록 τ_{1:t}(실행자 궤적·실험·스코어)을 분석하고 다음 라운드에서 사용할 하니스 (E_t, I_t)를 출력한다.
* 개선자는 실행자의 프롬프트·도구·워크플로우뿐 아니라 자신의 명령과 누적된 교훈(lessons)도 편집할 수 있다.
* improver는 자기 자신을 인자로 받아 재귀적으로 동작 가능.
* 종료와 평가: 예산 고갈 또는 진전 정체 시 종료.
* 최종 해 s_T의 테스트 스코어 S(s_T; D_test)를 보고 목표는 예산 내에서 테스트 점수를 최대화하는 것.
* 실행/평가 상세: 모든 모델은 동일한 시작 하니스 H_0와 스타터 솔루션에서 출발.
* 모델별 실행은 샌드박스에서 이루어져 검증/테스트 데이터 접근 불가.
* 다양한 작업별 주된 평가지표(예: SPL, t-mIoU, ARC RHAE, SRCC 등)를 0–100으로 정규화해 비교 및 순위 산출.
* 실험군: 18개 모델(클로즈드·오픈 혼합).
* 토큰·시간 사용 등 비용은 기록되어 분석에 포함됨.

## 주요 결과

- 전체 비교(랭킹 기준): Claude Opus 5.5가 전체 평균 점수 91.6으로 1위, Gemini 4 Argon 89.0, GPT-6.1 Sol 77.0, GPT-6 Astra 65.5. 최고 오픈-웨이트 모델 Qwen3.8-Flash-Next는 49.1로 5위(상대적 성능 격차 존재). (Figure 2)
- 자기개선 빈도 및 규모: 전체 177개 런 중 150개(85%)에서 검증 점수가 상승함. 중앙값 향상(검증 기준)은 10.4 포인트. 클로즈드 모델은 94%의 런에서 개선했고 중앙값 향상 14.9 포인트인 반면, 오픈-웨이트는 76%에서 개선 및 중앙값 향상 8.5 포인트였다. (Figure 3, 본문)
- 업종·작업별 차이: '해를 직접 구축(build the solution)'해야 하는 영역(예: Action, Reconstruction)에서 개선폭이 큼. 예시: 3D Tracking의 중앙 검증 점수는 19.4 → 62.2, RoboLab 8.3 → 45.8, Active Search 23.0 → 52.7. 반면 ARC-AGI-1/-2 같은 이미 스타터가 높은 점수를 갖는 작업은 개선 여지 적음(중앙 향상 0). (Section 4.3, Figure 3a)
- 피드백 해상도 효과: 각 에피소드별 연속적 스코어(범위형 피드백)는 모든 모델의 개선을 돕는 반면, 성공/실패(이진)만 기록하는 피드백은 특히 오픈-웨이트 모델의 개선을 제한한다(본문 결과 및 논의). (요약 및 Section 5 설명)
- 물리적·정확성 검사에서의 격차: 물리적 안정성이나 엄격한 정확성 검사가 요구되는 작업(예: RoboDojo, RoboCasa, 일부 Reconstruction·ARC-AGI-3)에서는 오픈-웨이트 모델이 특히 크게 뒤처짐. 겉으로 그럴듯해 보여도 엄격 검사에서 실패하는 사례가 빈번함. (본문 관찰 및 Table 사례들, Section 5.3 언급임).

## 한계

- 저자가 명시한 한계: Flex-RSI는 하니스(프롬프트·도구·워크플로우) 편집만 허용하며 모델 가중치(파라미터) 자체는 고정시킨다. 검증에서 매 라운드 정확한 점수를 사용하면 적응적 선택(adaptive selection) 위험이 있어 검증 분할/선택 문제와 과적합 위험이 존재함(본문 관련 논의, RRSI 등 참조). 또한 예산 및 검증 횟수 등 설정이 결과에 민감하며 과도한 검증 사용은 유의해야 한다.
- 본 연구 범위에서 드러나는 제약(분석적 한계, 본문에서 합리적으로 확인되는 한계):
  - 일부 작업(표에 나오는 4개)은 현재 적은 수의 모델(2개)로만 평가되어 일반화에 제약이 있음(본문 표 언급).
  - 클로즈드 모델은 제공자 API를 통해 접근하고 오픈 모델은 자체 GPU에서 서빙했으므로(운영·요금·지연·입출력 제약) 환경 차이가 성능·비용 분석에 영향을 미칠 가능성이 있음(본문에서 서비스 방식 명시).
  - 테스트 분할 및 평가기(validator/evaluator)가 고정되어 있어, 실제 배포환경의 다양성과 도메인적 차이를 모두 반영하지 못함.
  - 일부 작업은 스타터가 이미 높은 성능을 보여 개선 여지가 작아 RSI의 이점을 판단하기 어려움(예: ARC-AGI-1/-2, 일부 Perception 작업).

## 개발자 관점

- 벤치마크 재현성: 동일한 일반용 시작 하니스(H_0)와 스타터 솔루션, 개발/검증/테스트 분할을 공개·보관하면 하니스 편집 효과를 비교적 공정하게 측정할 수 있음. 다만 평가를 위해 검증·테스트 분할은 엄격히 비공개로 유지하고 실행자는 샌드박스화해야 함.
- 검증 수용 정책: 후보 해를 '검증 데이터에서 이전보다 δ 이상 향상될 때만 수용'하는 규칙(δ 초기값 = 스타터 검증 점수 표준편차 × 2)은 노이즈로 인한 과적합과 무의미한 수용을 줄이는 실용적 장치임. δ 값·검증 예산은 작업 성격에 맞게 조정할 필요가 있음.
- 피드백 설계의 중요성: 작업 에픽소드별 점수를 연속형(세분화)으로 반환하는 평가기는 개선을 촉진하니, 실제 시스템 설계 시 가능하면 세분화된 신호(연속 점수·부분 리워드)를 수집해야 한다. 성공/실패 이진 신호만 제공하면 특히 작은/오픈 모델에서 개선이 정체될 수 있음.
- 비용·예산 관리: 런 당 토큰 사용량은 매우 다양(중앙값 ~49.7M 토큰, 중간 80% 범위 8.6–93.4M). 더 많은 호출이 항상 더 나은 성능을 보장하지 않음(토큰 사용과 점수의 순위상관계 −0.05). 예산 설계·초기 라운드에서 빠른 수렴(대부분의 개선은 초반 라운드에 발생)을 고려한 조기 중단 전략이 유리함.
- 실행자·개선자 분리의 도입: 실행자(E)에게 '해를 구축하고 실험하는 책임'을, 개선자(I)에게 '하니스 자체를 수정'하는 책임을 부여하면 하니스 편집의 기여를 분리해 계량적으로 측정할 수 있음. 개발 시 두 컴포넌트를 명확히 분리·버전관리하고 실행 기록(trajectories)을 보존해야 함(디버깅 및 감사 목적).

**근거 범위:** 분석은 제공된 논문 PDF 본문(주요 본문과 표·그림·부록 예시)을 기반으로 작성되었다. 도출한 수치(예: 모델별 점수, 개선 비율, 토큰 중앙값, 작업별 검증 점수 변화 등)는 본문과 표에서 직접 확인 가능한 값만 사용했다. 다만 PDF 본문 일부가 반복/중복으로 추출된 부분이 있고(제출된 텍스트에 중복 페이지가 포함됨), 몇몇 작업은 아직 소수 모델로만 평가되어(본문에서 명시) 일반화에 제한이 있으므로 그 점을 반영해 서술했다. 본 분석에서 언급되지 않은 미세한 실험 세부(예: 각 런의 정확한 하드웨어 구성·정확한 요금 계산 등)는 PDF에서 직접 확인되지 않아 포함하지 않았다.
