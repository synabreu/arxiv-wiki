## 한 문장 요약

실행 시 메모리·시간 제약(실행 컨텍스트)을 생성 모델에 명시적으로 제공하면(‘컨트랙트 공개’) 코드 생성에서 메모리·시간 사용을 줄이고 구조적 구현 변화를 유도함을 고차원 유클리드 거리 계산 코드 생성 실험으로 증명한다.

## 해결하려는 문제

기존 자율 AI 에이전트는 계획(state)에서 실행 시간·메모리·런타임 제약 같은 실행 컨텍스트를 누락하는 경우가 많아(논문 용어: substrate blindness) 실제 환경에서 적절한 계획을 만들지 못한다. 본문은 특히 코드 생성 사례에서 실행 제약을 에이전트 입력으로 제공했을 때 모델이 구현 선택을 어떻게 바꾸는지(자원-시간 프로필과 정답성에 미치는 영향)를 묻는다.

## 핵심 기여

- 'substrate blindness' 개념을 제안하고 실행 컨텍스트를 1급 입력으로 다루는 필요성을 제기함.
- 세 가지 최첨단 모델(Anthropic Claude Opus 5, OpenAI GPT-5.6-Sol, Google Gemini 3.7 Flash)을 대상으로 한 통제된 코드 생성 실험 프로토콜을 제시하고, 작업만 제공하는 경우(task-only)와 실행 컨트랙트(예: 128 MB RAM 및 10.0 s wall-time) 공개의 효과를 비교함.
- 컨트랙트 공개가 Peak 메모리(MaxRSS)를 감소시키고 평균 실행 시간을 줄였으며(최대 3.1x 가속), 구체적이고 반복 가능한 구조적 코드 변경(예: bounded blocking, float32 유지, upper-triangle 순회, in-place 또는 memory-mapped 버퍼)을 유도함을 실증함.
- 더 타이트한 컨트랙트(96 MB) 조건에서 독립 표본의 컨트랙트-공개 코호트가 '정답이면서 예산 내' 결과를 상당히 더 자주 달성함을 보였음(Claude 4/5, GPT-5.6-Sol 5/5, Gemini 3.7 Flash 3/5 vs task-only 0/5,1/5,0/5).
- 컨트롤된 proof-of-concept으로서 최소한의 실행 컨트랙트만으로도 생성 프로그램이 사전(실행 전)적으로 구조적 적응을 하여 비효율적 할당에서 계산을 이동시킨다는 점을 제시함.

## 접근 방법

* 본문 기준으로 수행된 접근은 다음과 같다: 모델·설정 - Anthropic Claude Opus 5, OpenAI GPT-5.6-Sol, Google Gemini 3.7 Flash의 '프론트라인' 구성들을 사용.
* 실험 과제 - 고차원(pairwise) 유클리드 거리 계산을 수행하는 코드 생성 과제.
* 처리 조건 - 두 가지(또는 여러) 프롬프트/입력 조건을 비교: (1) task-only(작업 서술만 제공), (2) 컨트랙트 공개(예: 128 MB RAM 및 10.0 s wall-time을 명시).
* 추가로 더 타이트한 96 MB 컨트랙트 실험을 별도로 수행.
* 측정 및 비교 - 생성된 코드의 실행을 통해 측정한 Peak process memory(MaxRSS)와 wall time(실행 시간)을 주요 지표로 삼아 task-only 대비 컨트랙트-공개의 효과를 정량 비교.
* 관찰 - 실행 결과와 생성된 코드 구조를 감사(audit)하여 메모리·시간 절감과 연관된 구현 패턴(예: float32 사용, 상삼각만 순회, in-place 연산, memory-mapping 등)을 수집.
* (본문에 따르면 모델 파라미터 수정·사전학습 변경은 없고, 컨트랙트는 입력으로서의 차이만 적용된 것으로 서술됨.)

## 주요 결과

- 컨트랙트(예: 128 MB/10.0 s) 공개는 실행 가능한 인덱스 정렬(executable index-aligned) 비교에서 14건 중 13건에 대해 측정된 Peak 프로세스 메모리를 감소시켰음.
- 평균 wall time은 세 모델 코호트 모두에서 감소했으며, 최대 3.1배까지 실행이 빨라짐을 보고함.
- 생성 코드에서 관찰된 구조적 변화로는 bounded blocking(경계가 있는 블로킹/배치 처리), float32 유지(더 낮은 정밀도 사용), 상삼각(upper-triangle)만 순회해 계산량·메모리 절약, in-place 연산 또는 memory-mapped 버퍼 사용 등이 있음.
- 96 MB로 더 타이트한 컨트랙트에서 독립 표본의 컨트랙트-공개 코호트 성과: Claude Opus 5 4/5, GPT-5.6-Sol 5/5, Gemini 3.7 Flash 3/5가 '정답이면서 예산 내' 결과를 냈음. 같은 task-only 기준은 각각 0/5, 1/5, 0/5였음.
- 코호트 평균으로 보았을 때 MaxRSS는 task-only 대비 49–74% 낮아졌고, wall time은 35–64% 낮아졌음.

## 한계

- 저자 명시(본문에 직접 언급된 한계): 본 연구는 '통제된 proof-of-concept'로 제시되어 실험 범위와 일반화 가능성이 제한적임(즉, 코드 생성의 특정 수치 실험에 대한 증거를 제공하는 수준임).
- 본문 기반으로 확인되는 제약(분석가 추정): 실험이 한 가지 작업 유형(고차원 유클리드 거리 계산)과 세 가지 모델 구성에 국한되어 있어 다른 작업(자연어 계획, 로봇 제어 등)이나 더 다양한 모델·버전으로의 일반화가 불분명함.
- 본문에 제시된 수치와 결과는 있지만, 프롬프트 문구, 샘플링(seed·temperature), 실행 환경(운영체제·파이썬/라이브러리 버전), 코드 실행 허용/제한 방식 등 재현에 필요한 상세 설정들이 본문(제공된 텍스트)에서 확인되지 않아 완전한 재현이 어렵다.
- 통계적 유의성 검정, 표본 수에 대한 전면적 보고, 실패 케이스 분석의 세부 내용은 제공된 본문 범위에서 충분히 확인되지 않음(예: 14건 중 13건이라는 보고는 있지만 각 비교의 샘플 수·분산·신뢰구간 등은 누락되어 있음).

## 개발자 관점

- 에이전트·생성 모델에 실행 제약(메모리·시간)을 명시적으로 입력으로 제공하면 런타임 친화적 구현을 유도할 수 있으므로 실제 배포 환경에서는 컨트랙트(예: 사용할 수 있는 RAM, 최대 허용 실행시간)를 프롬프트에 포함시키는 것을 권장함.
- 리소스 제약을 명시할 때 작은(타이트한) 예산을 실험해보면 모델이 더 적극적으로 구조적 최적화를 도입함(예: in-place 연산, float32로 정밀도 낮추기, upper-triangle 순회, memory-mapping).
- 배포 전에는 단순 정확성 외에 '정답이면서 예산 내(correct-and-within-budget)' 지표를 설정하고 여러 독립 표본으로 평가해 일관성을 확인해야 함(본문은 N=5 코호트 결과를 제시함).
- 실행 프로파일(특히 MaxRSS와 wall time)을 자동 측정 파이프라인에 포함시키고, 모델이 생성한 코드를 실행 전(정적 분석 또는 실행 샌드박스)·후(실제 실행)로 감사(audit)하여 비효율적 패턴을 찾아내야 함.
- 프롬프트 기반 방법이므로 프롬프트 문구와 샘플링 변동성에 민감할 수 있으니, 다양한 프롬프트·랜덤 시드로 반복 실험하고 실패 케이스를 수집해 리스크를 관리해야 함. 본문에 자세한 재현 정보가 부족하므로 자체적인 표준화(환경·라이브러리·측정법)를 마련할 것. 

**근거 범위:** 논문 PDF 본문 기반 분석: 제공된 본문(및 초록으로 보이는 중복 단락)을 근거로 정리함. 다만 원문 전체 PDF 추출에 실패했다는 메모가 있어(제공 텍스트가 한정적임) 프롬프트 정확한 문구, 실행 환경 세부사항, 전체 실험 수·통계 처리 방식 등 본문에 포함되어 있을 수 있는 상세 정보는 확인하지 못했음. 따라서 제시된 수치와 관찰(예: 13/14, 3.1x, 4/5 등)은 제공된 본문에 명시된 내용만을 직접 인용했으며, 추가 재현·확장에는 원문 전체의 추가 세부사항 확인이 필요함.
