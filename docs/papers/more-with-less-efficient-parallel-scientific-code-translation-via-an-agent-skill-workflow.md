## 한 문장 요약

병렬 과학 코드를 OpenMP/CUDA/SYCL 간에 자동으로 번역하기 위해 번역·컴파일진단·실행검증을 분리한 에이전트-스킬(agent-skill) 워크플로우를 제안하고, verdict 기반 라우팅으로 실패를 특정 수리(skill)로 보낼 때 더 높은 검증된 정합성과 토큰 효율을 달성함.

## 해결하려는 문제

병렬 과학 컴퓨팅에서는 수치적 동등성(부동소수점 허용오차), 실제 GPU 오프로딩 여부, 병렬결과의 결정성 등 도메인 특화된 정확성 기준이 필요하다. 기존 LLM 기반 파이프라인(예: LASSI 등)은 고정된 순차 워크플로우로 모든 오류에 동일한 수리 전략을 적용하고(무차별 재시도), 컴파일 성공 또는 표면적 출력 매칭으로 과도하게 성공을 판단하며, 오류 원인별 동적 라우팅과 자동화된 의미 검증이 부족하여 불필요한 LLM 호출과 토큰 낭비, 그리고 과대평가된 성공률을 초래한다.

## 핵심 기여

- 병렬 과학 코드 번역을 위해 번역(TranslationAgent), 컴파일 진단(CompilationAgent), 실행 검증(ExecutionAgent)을 분리한 에이전트-스킬 아키텍처와 verdict 기반 오케스트레이터를 제안함(진단별로 적합한 수리 스킬로 라우팅).
- 자동화된 출력 검사(실행에서의 FAIL 마커·종료코드 기준)를 1차 검증으로 두고, 컴파일/런타임 검사를 회피하는 허위 성공을 잡아내기 위한 오프라인 LLM 기반 보완 검증기를 도입함.
- 컴파일 오류·런타임 오류 유형에 따라 Patch, MemoryRepair, SemanticRepair, SyncRepair 등 목표지향 수리 스킬을 사용해 불필요한 재생성(retry)을 줄이고 토큰 효율을 높임.
- HeCBench의 30개 커널을 대상으로 CUDA↔OpenMP↔SYCL의 6개 방향과 세 개 오픈소스 LLM(DeepSeek V4 Flash, GLM-5.2, Kimi K2.7-Code)에서 LASSI 대비 모든 모델·방향 조합(18개)에서 더 높은 검증된 정확도를 달성하고 토큰을 최대 52.4% 절감했음을 실험적으로 보임.
- 아키텍처가 방향-무관(direction-agnostic)이며, 번역 페어는 런타임에 교체 가능한 스킬 구현으로 확장 가능함(새 대상 언어는 스킬/프롬프트 추가로 지원).

## 접근 방법

* 시스템은 중앙 오케스트레이터와 세 개의 에이전트로 구성된다.
* TaskState(공유 상태)를 통해 현재 번역 코드, 컴파일/실행 산출물, 메타데이터를 유지하며, 각 단계는 Verdict(분류된 결과)를 반환한다.
* TranslationAgent는 AnalyzerSkill(프레임워크 독립적 기능 요약), MemoryPlanningSkill(대상 모델용 메모리·데이터 레이아웃 계획), TranslatorSkill(요약+메모리 계획을 반영한 대상언어 코드 합성)을 순차 실행한다.
* CompilationAgent는 CompilerSkill(실제 컴파일 호출)과 ErrorClassifierSkill(컴파일 로그 기반 트리거 조건표(Table I)에 따라 링크·문법·API 오용·메모리 관련 오류 등으로 분류)을 포함한다.
* ExecutionAgent는 RunnerSkill(바이너리 실행, stdout/stderr/exit code 수집)과 RuntimeAnalysisSkill(타임아웃, FAIL 마커, 비정상 종료 등으로 분류)을 포함한다.
* 오케스트레이터는 각 Verdict를 읽고 routing table에 따라 해당 결함에 특화된 repair skill(PatchSkill, MemoryRepair, SemanticRepair, SyncRepair 또는 재번역)을 호출한다.
* 자체 수정 루프는 통일된 self-correction 예산(수리 호출만 카운트)과 최대 재시도 횟수로 제한되며, RunnerSkill은 실행 타임아웃 시 입력 인자 축소(스케일링, 기본 5회까지)로 검증 가능한 입력 크기로 자동 조정한다.
* 루프 내부 검증(in-loop)은 컴파일 성공 + exit code 0 + FAIL 마커 부재를 EQUIVALENT로 처리해 최종 수락을 결정하고, 오프라인 LLM 기반 보완 검증기는 캐시된 원본 프로그램·실행 출력을 받아 사후평가(통과/실패 및 신뢰도 점수 0–1)만 수행하여 in-loop의 위양성(false positive)을 식별한다.

## 주요 결과

- 데이터셋·설정: HeCBench에서 대표적으로 선택한 30개 커널(표 III), 세 개 LLM(DeepSeek V4 Flash, GLM-5.2, Kimi K2.7-Code), 6개 방향(CUDA↔OpenMP↔SYCL). 컴파일러: g++ 8.5.0, nvcc 12.8, icpx/dpcpp 2021.4.0. 컴파일 한도 300s, 실행 한도 120s, 수리 루프 최대 9회(재현 제안에서는 5회 사용 예시).
- 정량적 성능(주요 발췌): DeepSeek V4 Flash에서 CUDA↔OpenMP 쌍: 본 기법은 CUDA→OpenMP 93.3% 및 OpenMP→CUDA 95.8%의 검증된 정답률을 기록(대조 LASSI: 86.7%, 87.5%). 동일 설정에서 토큰 사용량은 본 기법 718k/835k(각 방향) 대 LASSI 1,327k/1,058k로 각각 약 45.9%·21.1% 감소(표 IV).
- 모든 모델·방향(18개)에서 본 기법이 LASSI보다 높은 검증된 정확도를 달성. 모델별 평균 정답률: DeepSeek 평균 88.7% vs LASSI 65.5%; GLM 78.6% vs 34.5%; Kimi 94.6% vs 54.8%(표 IV 합계). 평균 토큰 소비는 논문 기준 방향당 본 기법 1,071k vs LASSI 1,451k(약 26.2% 감소), 모델별 토큰 절감 폭은 29.5%–52.4% 범위.
- 보완 검증 적용 결과: in-loop 기준 성공률은 전체 70.1%였으나 LLM 보완 검증 적용 시 58.4%로 감소(총 999개 아티팩트 중 117건(11.7%)이 in-loop의 위양성으로 판정, 표 V 및 VI). 보완 검증의 중앙 신뢰도는 0.95이며 79.3% 판정이 ≥0.9 신뢰도를 가짐(그림 3).
- 비용 대비 효과: 보완 검증 기준으로 검증된 성공 1건당 토큰 비용은 본 기법이 46k–54k(모델별)인 반면 LASSI는 112k–184k으로, 본 기법이 2.1–3.9배 더 저비용임을 보고함. 또한 수리 루프는 대체로 초반(약 5회 이내)에 대부분의 개선이 발생하고 그 이후에는 수확 체감이 관찰됨(섹션 V).

## 한계

- 저자가 명시한 한계(논문 본문에서의 진술): (1) 평가는 커널 수준(HeCBench)에서 이루어졌으며 멀티파일 프로젝트·전체 응용프로그램으로 확장하려면 교차 파일 분석·빌드 시스템 인식·번역 상태 지속이 필요함; (2) LLM 기반 보완 검증기는 개선 여지가 있고(평가 룰 개선, 다중 검증자 투표, 신뢰도 기반 재실행 연계 등), 현재는 오프라인·사후 평가 용도로만 사용됨; (3) 성능(퍼포먼스)을 보수 루프에 포함하지 않아 성능 보장(성능 회귀 방지)은 향후 작업으로 남음(섹션 VI).
- 실험·방법에서 확인되는 제약(본문 근거로 합리적 확인된 한계): (1) 선택한 평가 집합은 논문에서 대표성 목적으로 선정한 30개 커널이며, 6개 커널은 OpenMP 구현이 없어 OpenMP-소스 방향은 24개씩 평가됨(섹션 IV-A); (2) 실험에 사용된 컴파일러·버전(g++ 8.5.0, nvcc 12.8, icpx 2021.4.0) 및 실행 환경(DeepBlizzard 클러스터·Slurm)이 결과에 영향을 줄 수 있음; (3) 보완 검증은 오프라인으로 루프에 피드백을 주지 않으므로 in-loop에서 통과한 산출물을 자동으로 수정하지 않음; (4) 일부 LASSI 실행(Kimi K2.7-Code에 대해 9건)은 출력이 없어 제외됨—모델·인터페이스 안정성의 영향 가능성(본문 언급).

## 개발자 관점

- 재현·구현: 저자 제공 저장소(논문 부록에 URL 명시)를 통해 오케스트레이터·에이전트·스킬 구현과 LASSI 설정 및 배치 실행 스크립트를 제공함. 요구 소프트웨어는 Python3.9+, OpenAI 호환 LLM 엔드포인트(모델 이름·API 키), g++ 8.5.0, CUDA 12.8, Intel oneAPI DPC++/C++ 2021.4.0 등이며 Slurm 관리 GPU 노드가 필요함(부록의 Artifact Setup 및 실행 절차 참고).
- 운영·비용: verdict 기반 라우팅과 전용 수리 스킬로 불필요한 전체 재번역을 줄여 LLM 토큰 비용을 크게 절감할 수 있음(논문 실험에서 모델별 29.5%–52.4% 토큰 절감 보고). 단, 초기 초안 품질이 낮으면 수리 라운드가 늘어나며 초반(대략 5회) 이후 수확 체감이 나타나므로 self-correction 예산·최대 재시도 횟수를 실무 제약에 맞춰 설정해야 함.
- 확장성: 번역 논리를 스킬로 캡슐화했으므로 새로운 소스→타겟 페어는 페어별 스킬(프롬프트 포함) 구현만으로 추가 가능 — 멀티파일·빌드시스템 지원을 추가하려면 상태 지속, 교차-유닛 분석, 빌드 스크립트 처리 스킬이 필요함.
- 검증·안전성: 단순 컴파일·런타임 체크만으로는 위양성(placeholder 구현, 검증 누락, 수치오류 등)이 발생하므로 오프라인 LLM 기반 보완 검증 또는 사람의 샘플 확인을 권장함. 논문 실험에서는 보완 검증이 false negative를 발생시키지 않았으나 in-loop의 위양성을 11.7% 식별했음(표 V·VI).
- 운영상 권장 설정: 컴파일 타임아웃 300s, 실행 타임아웃 120s, 수리 루프 최대 5~9회(논문은 기본 9회, 재현 예시는 5회), 자동 입력 축소 기법으로 과도한 입력 크기 문제를 제어. 또한 통합 self-correction 예산을 두어 무한 재시도를 방지할 것.
