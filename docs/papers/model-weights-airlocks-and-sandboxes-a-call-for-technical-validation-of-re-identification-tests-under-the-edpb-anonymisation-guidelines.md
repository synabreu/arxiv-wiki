## 한 문장 요약

EDPB의 익명화 지침에서 재식별(리-아이덴티피케이션) 테스트의 설계·검증 방법이 빠져 있다는 문제를 다루며, 보안 처리 환경(SPE)과 에어록(출력 검토) 틀에서 테스트를 측정법으로 검증(검출한계·편향·불확실성 명시)할 것을 제안한다.

## 해결하려는 문제

EDPB Guidelines 02/2026는 익명성 평가를 '어떤 주체가 어떤 수단을 합리적으로 사용할 수 있는가' 관점에서 규정하고 AI 모델을 평가대상에 포함시키며 테스트와 문서화를 요구하지만, 재식별 테스트를 어떻게 설계·검증하고 그 결과를 어떤 근거로 증거로 삼을지에 대한 기술적 지침이 부재하다. 이로 인해 실패한 재식별 시도가 '데이터가 안전하다'를 의미하는지, 아니면 '테스트가 약해서 못 찾은 것'인지 판별하기 어렵고, 테스트의 편향·검출한계·불확실성이 보고되지 않아 법·규제적 판단에 사용하기 어렵다.

## 핵심 기여

- 보안 처리 환경(SPE)과 에어록(출력 검토)을 중심으로 두 가지 EDPB 접근(문맥적 접근 vs 단순화된 접근)을 적용할 공통 프레임워크를 제시하고, 릴리스 형태(레코드·집계·모델 가중치·쿼리 서비스)와 증거 유형(형식적·경험적·간접적)을 구분함 (Sect.3).
- 재식별 테스트·AI 모델·보안 환경 적용과 관련된 7개의 공개 질문과 각 질문별 시나리오를 제시하여 추가 법·기술 연구가 필요한 쟁점을 명시함 (Sect.4).
- 모델 가중치 공개, 에어록에서의 검토, 규제 샌드박스의 감독 테스트 등 세 환경별로 기술적 고려사항(공격자 가정·테스트 신뢰도·철회 불가성 등)을 분석하고 논의함 (Sect.5).
- 재식별 테스트를 다른 규제 분야의 측정 관행처럼 '측정 방법(method) 검증' 대상으로 보고, 검출한계·편향·불확실성을 명시하도록 검증·보고 체계를 요구함(시험 프로토콜 고정, 검증용 기준 사례, 보고서 항목 제안).

## 접근 방법

* 본 연구는 개념·정책 분석과 설계 제안을 중심으로 한다.
* 핵심 요소는 1) 보안 처리 환경(SPE): 내부의 역할·수단이 알려져 통제 가능한 환경에서 데이터 처리를 하고, 2) 에어록(airlock) 출구 검토: 모든 출력은 에어록 심사를 거쳐 배포 여부를 결정하며, 수신자가 알려진 경우에는 문맥적 접근, 공개·임의 수신자 대상일 경우 단순화 접근 적용을 권고한다.
* 출력 형태(레코드, 집계, 합성데이터, 모델 가중치, 쿼리 서비스)를 구분하고 각각이 수신자에게 제공하는 공격 표면을 분석한다.
* 증거는 형식적(예: differential privacy 보장), 경험적(공격 기반 테스트: 멤버십 추론·데이터 추출 등), 간접적(훈련 문서·리스크 지표)으로 구분한다.
* 제안된 절차는 사전 위험 전수조사(프리스크리닝) → 필요시 공격 테스트(프로토콜·공격모델·측정지표 사전 고정) → 테스트 보고서(검출한계·편향·불확실성·가정·재평가 조건 명시)로 구성된다.
* 또한 테스트 방법은 측정법으로서 기준 사례(reference cases)에서 검증되어야 하며(검출한계·편향·불확실성 산정), DP 보증의 감사(audit)와 경험적 테스트를 상호보완적으로 사용하도록 제안한다.

## 주요 결과

- 개념적/정책적 프레임워크 제시: SPE + 에어록 틀을 통해 '누가 받는가'에 따라 문맥적·단순화된 접근을 명확히 구분하고, 릴리스 형태와 증거 유형을 정리함(Sect.3).
- 실무적 쟁점 목록화: 모델 가중치 공개, 쿼리 서비스, 철회 불가 릴리스, 형식적 보증(예: DP)의 단순화 접근 적용 조건, 간접증거의 충분성 등 7개의 구체적 공개 질문과 시나리오 제시(Sect.4).
- 테스트를 측정법 관점에서 검증해야 한다는 주장의 구체화: 검증 대상(검출한계·편향·불확실성), 검증 방법(기준 사례에의 적용), 테스트 보고서가 담아야 할 항목들(검토 대상·가정·프로토콜·검출한계·불확실성·개별 기록에 대한 결과 등)을 제안함(Sect.5, Method validation 및 부록).
- 형식적 보증(DP)과 경험적 테스트의 관계 정리: DP는 모든 공격에 대해 상한을 제공하나 파라미터·프라이버시 단위·변형에 따라 의미가 달라지고, 경험적 감사는 하한(실제 관찰 가능한 누수)을 제시하여 둘이 보완관계에 있음(부록 D).
- 테스트 운영 실무 권고: 사전 리스크 스크리닝, 테스트 프로토콜 고정, 독립성 확보, 테스트 결과의 불확실성·검출한계 보고, 재평가 트리거 명시 등 구체적 보고·운영 지침을 제시함(Sect.5 및 부록 A).

## 한계

- 저자가 명시한 한계: 논문은 기술적 관점에서 쟁점을 제기하고 기술적 고려사항을 분석하되, 법적 해석과 최종 규범적 판단은 다루지 않음(즉, 일부 공개 질문은 법적 판단 필요). 또한 여러 질문을 '열린 문제'로 남겨 구체적 해법(예: DP 파라미터 값 지정 등)은 제시하지 않음(Sect.5).
- 본문에서 확인되는 추가 한계: 경험적·정량적 실험이나 사례 연구(예: 대규모 모델에 대한 실제 테스트 결과)가 없음—제안은 주로 개념적·절차적 권고임. DP 파라미터(ε, δ)나 재식별 허용 기준의 구체적 수치와 같은 운영값은 제시되지 않아 실무 적용 시 추가 연구·합의가 필요함. 테스트 방법 검증(검출한계·편향·불확실성 산정)의 구체적 통계적 절차·표준화 방안은 초안 수준으로 남아 있음. 또한 매우 큰 모델이나 리소스가 제한된 환경에서의 현실적 테스트(참조 모델 수 제한 등)에 대한 구체적 대안은 제시가 제한적임.

## 개발자 관점

- 테스트를 설계할 때 이를 '측정 방법'으로 보고 사전 검증(기준 사례에서의 검출한계·편향·불확실성 산정)을 수행하라. 검증된 방법만이 에어록·샌드박스에서 증거로 제출될 수 있다.
- 출력 형태(가중치 파일 vs 쿼리 서비스)에 따라 가정해야 할 공격자 수단이 달라지므로 테스트 프로토콜(쿼리 예산·응답 타입 등)을 릴리스 형태에 맞춰 사전 고정하라. 공개된 가중치는 철회 불가성을 고려해 더 강한 마진 또는 형식적 보증이 필요하다.
- 테스트 프로토콜과 판단 기준을 테스트 전(사전)에 고정하라. 결과를 본 뒤 임계값·공격 선택을 바꾸면 우연성으로 유리한 결과를 얻을 위험이 있다(사전 등록 원칙).
- 테스트 보고서에 반드시 포함할 항목들을 표준화하라: 대상 릴리스·수신자 가정·실행된 공격·검출한계·편향·불확실성·결과(전체·최취약 레코드)·재평가 조건·검증자 독립성 등. 특히 검출한계를 명시하면 ‘발견하지 못함’의 의미를 해석 가능하게 한다.
- 검증·평가 기능은 개발자·제품 소유자와 독립된 주체가 수행하거나, 규제 샌드박스에서 권한있는 감독자가 사전검토·검증을 수행하도록 설계하라. 테스트는 원천데이터를 필요로 하므로 에어록 내에서 수행되며 테스트 자체도 개인정보 처리의 법적 근거·기록 대상임을 인식하라.
