## 한 문장 요약

강력한 LLM 백본을 동일한 시간 예산으로 사용할 때, 복잡한 다중 에이전트·검색 등 하니스는 최소한의 read/write/bash 접근을 가진 단일 세션 코딩 에이전트 대비 성능 이점이 없어 하니스 설계 노력이 현재 MLE 벤치마크에서 비효율하다는 것을 대규모 절제 실험으로 보인 연구.

## 해결하려는 문제

최근 자율적 머신러닝 엔지니어링(MLE) 에이전트들은 긴 목표 주기와 제한된 LLM 원시 명령 때문에 다중 에이전트 오케스트레이터, 전용 검색 서브에이전트 등 점점 더 복잡한 하니스(도구·인프라)를 쌓아왔다. 이런 설계가 실질적 이득을 주는지, 아니면 강력한 LLM 백본과 직접 실행환경(read/write/bash)에 접근하는 단순한 코딩 에이전트로도 동일한 성능을 낼 수 있는지가 미해결 문제다.

## 핵심 기여

- 동일한 시간 예산과 동일한 LLM 백본을 전제로, 오픈소스 최신 하니스(복잡한 오케스트레이션·검색 계층 등)가 최소 하니스 코딩 에이전트(single-session)에 비해 성능 우위를 제공하지 않는다는 경험적 증거를 제시함.
- 코딩 에이전트 설정에서 하니스 계층들이 중복적(redundant)이라는 주장을 뒷받침하는 대규모·체계적 절제(ablation) 연구를 수행함.
- 성능의 주요 동인은 하니스가 아니라 LLM 백본 자체라는 관점을 실험적으로 제시함.
- 최소 하니스 코딩 에이전트(single-session, 실행환경 직접 접근)를 비교 기준(base-line)으로 설정하고 평가함.
- 현행 MLE 벤치마크에 대한 하니스 설계 노동의 투자 대비 효용이 낮다는 실무적 결론을 제시함.

## 접근 방법

* 연구는 동일한 총 시간 예산과 동일한 최첨단 LLM 백본을 고정한 조건에서 두 가지 체계적 비교를 수행한다: (1) 오픈소스 상태의 복잡한 하니스(예: 다중 에이전트 오케스트레이터, 전용 검색/리트리벌 서브에이전트 등)를 사용하는 기존 에이전트들, (2) 단일 세션의 최소 하니스 코딩 에이전트(LLM이 실행환경에 직접 접근할 수 있는 read, write, bash 등의 원시 프리미티브만 부여된 에이전트) 를 비교한다.
* 또한 여러 구성요소를 제거·변형하는 대규모 절제 연구를 통해 어떤 하니스 계층이 성능에 기여하는지를 분석한다.
* 평가 절차는 공개된 MLE 리더보드/벤치마크 상의 성능 비교(논문 본문에서 구체적 데이터셋/메트릭 명시는 제공되지 않음)를 기반으로 한다.

## 주요 결과

- 동일한 시간 예산과 동일한 LLM 백본 하에서, 오픈소스 상태의 복잡한 하니스는 단일 세션 최소 하니스 코딩 에이전트에 대해 명확한 성능 우위를 제공하지 못함.
- 대규모 절제 실험 결과 하니스의 여러 계층(오케스트레이터, 검색 서브에이전트 등)은 코딩 에이전트 설정에서 중복적이거나 불필요한 것으로 나타났음.
- 전체적인 해석은 성능 개선의 주된 원천이 하니스 설계가 아니라 LLM 백본 자체라는 것임.

## 한계

- 저자가 본문(제공된 초록)에서 명시적으로 밝힌 한계는 제공된 텍스트에 없음.
- 추론가능한 실험 범위의 제약: 결과는 '동일한 시간 예산'과 '동일한(강력한) LLM 백본' 조건 하에서 나온 것으로, 약한 백본이나 다른 시간 예산(예: 장기간 온라인 학습, 반복적 멀티세션 설정)에서는 결론이 달라질 수 있음.
- 평가 대상과 데이터셋, 메트릭 등의 상세 정보가 본문(초록)에서 제공되지 않아 결과의 일반화 가능성(다른 벤치마크·도메인·작업군에 대한 적용)은 불확실함.
- 구체적 구현·튜닝 세부사항(사용한 LLM 종류·버전, 하니스 구현체와 설정, 하이퍼파라미터, 실험 환경)은 확인되지 않아 재현성에 제약이 있음.

## 개발자 관점

- 우선순위: 복잡한 하니스 개발에 많은 공수를 들이기보다, 가능한 경우 더 강력한 LLM 백본을 도입하거나 백본 성능 개선에 자원 투입하는 것이 벤치마크 성능 개선에 더 효율적일 수 있음.
- 단순성/유지보수: 최소 하니스(직접 실행환경 접근을 허용하는 코딩 에이전트)는 구현·운영·유지보수 비용이 낮아 빠른 프로토타이핑과 재현성을 높일 가능성이 있음.
- 재현과 비교 실험: 동일한 시간 예산과 동일한 백본을 고정하는 실험 설계를 유지해 하니스 설계의 순수한 기여를 평가해야 함.
- 안전·운영 리스크: LLM이 직접 read/write/bash를 통해 환경에 접근하면 보안·안전 위험(임의 코드 실행, 데이터 유출, 시스템 손상 등)이 증가하므로 샌드박스, 권한 제한, 로깅 및 감사 체계를 반드시 병행해야 함.
- 비용·배포: 복잡한 멀티에이전트 하니스는 개발·인프라 비용과 운영 복잡도를 증가시키므로, 비용 대비 성능 이득이 불분명할 때에는 단순 에이전트 접근이 더 경제적일 수 있음.
